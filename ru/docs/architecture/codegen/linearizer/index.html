Фаза 4: Linearizer

Цель: Преобразовать DAG в линейную последовательность инструкций.

Стадия 16: Пост-индексная символика​

Стадия кратко

Цель: Полное символическое упрощение после понижения индексов Ключевые паттерны: Все символические правила (140+) Эффект: Финальная чистка перед сериализацией

Что делает: Полное символическое упрощение после понижения индексов.

Зачем это нужно: Теперь, когда индексы стали конкретными целыми (i32/i64), арифметика может полностью упроститься. Это последний шанс вычистить выражения перед линеаризацией.

Паттерн: symbolic

В Svod нет операции GEP — адресация выражается как INDEX(STACK(...)) — поэтому у gep_pushing из Tinygrad здесь нет аналога. Ближайший аналог — alu_vectorize_reorder_patterns:

Before:  ADD(STACK(x, x, x, x), STACK(y, y, y, y))
              ↓ [Reorder ALU over STACK]
After:   STACK(ADD(x, y), ADD(x, y), ADD(x, y), ADD(x, y))

Зачем? Даёт возможность свёртки констант и скалярной оптимизации на схлопнутой операции. Это правило живёт в sym() уровня 3, поэтому оно уже сработало на стадии 14, а не здесь.

Стадия 17: Pre-Matcher (опциональная)​

Стадия кратко

Цель: Бэкенд-специфичные паттерны перед декомпозицией Ключевые паттерны: Специфичные для рендерера Эффект: Аппаратно-специфичные оптимизации

Что делает: Специфичные для рендерера паттерны, применяемые до декомпозиции.

Зачем это нужно: Каждый бэкенд может добавить свои паттерны. Например, DSP-бэкенды используют это для замены общих паттернов на DSP-специфичные SIMD-интринсики. Это позволяет выполнять аппаратно-специфичные оптимизации, не трогая общий пайплайн.

Паттерн: renderer.pre_matcher

Большинству бэкендов (CPU, GPU) это не нужно. Только специализированное железо использует эту стадию.

Примечание: В Svod нет pre_matcher. Бэкенд-хуки живут в трейте svod_device::device::Renderer (device/src/device.rs): decompositor(), extra_matcher(), pre_isel_matcher() и isel_matcher(). Последние два выполняются на границе PROGRAM, между стадиями 20 и 21, а не перед декомпозицией. (svod_codegen::traits::Renderer — отдельный, более узкий трейт с render(), backend_name() и decompositor().)

Стадия 18: Декомпозиции​

Стадия кратко

Цель: Переписать операции, которые целевое железо не поддерживает Ключевые паттерны: Степени двойки, аппроксимации трансцендентных функций Эффект: Маппинг высокоуровневых операций на аппаратные инструкции

Что делает: Поздние перезаписи для операций, которые целевое устройство не поддерживает.

Зачем это нужно: У железа нет всех операций. Например, у большинства CPU нет прямой инструкции sin. Мы аппроксимируем её через операции, которые существуют (сложение, умножение и т.д.).

Паттерн: early_decomposition_patterns() + get_late_rewrite_patterns() + get_transcendental_patterns() (плюс renderer.decompositor(), если бэкенд его предоставляет). Сам early_decomposition_patterns() начинается с symbolic_simple().

Примечание: pm_split_ends() не входит в этот проход — он вложен в матчер стадии 19 и запускается снова в начале стадии 20.

ПаттернПримерКогда используется
MOD → ANDx % 8 → x & 7Степень двойки в делителе
MUL → SHLx * 16 → x << 4Степень двойки в множителе
DIV → SHRx / 8 → x >> 3Степень двойки в делителе (CDIV в стиле C)
FDIV → MULx / 2.0 → x * 0.5Константа в float-делителе
NEGx * -1 → NEG(x)Когда NEG поддерживается
MULACCa * b + c → MULACC(a, b, c)Когда FMA поддерживается
Быстрое целочисленное делениеx // 7 → (x * M) >> SДелитель не степень двойки
Законы Де Моргана(!x) & (!y) → !(x | y)Булево упрощение (только AND-от-NOT)
Отрицания сравнений!(x < c) → (c-1) < xЦелочисленные сравнения

Аппроксимации трансцендентных функций (EXP2, LOG2, SIN, …) приходят из get_transcendental_patterns() (ir/src/decompositions/mod.rs, реализации в ir/src/decompositions/transcendentals.rs). Они включаются пооперационно, когда у рендерера нет соответствующей инструкции, или для всех операций при TRANSCENDENTAL=2. Опциональный хук Renderer::decompositor() добавляет сверху бэкенд-специфичные правила; ни один встроенный бэкенд его не использует.

Svod: optimizer/mod.rs

Стадия 19: Финальная перезапись​

Стадия кратко

Цель: Подготовка к линеаризации Ключевые паттерны: Фиксация слабых кастов, перезаписи рендерера, разделение END Эффект: Чистое представление, готовое к линеаризации

Что делает: Подготовка к линеаризации.

Зачем это нужно: Некоторые паттерны проще применить после декомпозиции. Эта стадия делает финальную чистку перед преобразованием в линейную последовательность.

Паттерн: pm_commit_weak() + pm_cast_weak() + pm_decomp (декомпозиции стадии 18), плюс renderer.extra_matcher() и pm_split_ends() — все они суммируются в один матчер. Затем отдельными проходами выполняются pm_remove_invalid() и add_implicit_barriers().

Примечание: extra_matcher и pm_split_ends — часть этого объединённого матчера, а не отдельные проходы. В Svod нет шага векторизации CONST или разрешения GEP; у pm_render из Tinygrad здесь нет аналога.

Разделение многодиапазонных END:

// Before: END closing multiple ranges
END(op, [range_a, range_b])

// After: nested single ENDs
END(END(op, range_a), range_b)

RANGE сортируются по убыванию (axis_id, axis_type.priority()), поэтому самый внутренний END строится первым. Источники-«обратные рёбра» типов Void/Bool отделяются и переприкрепляются к самому внешнему END с сохранением исходного тега.

extra_matcher: Каждый бэкенд может добавить свои финальные паттерны. Это позволяет выполнять аппаратно-специфичные оптимизации, не трогая общий пайплайн.

Svod: optimizer/mod.rs, linearize/mod.rs

Стадия 20: Добавление управления потоком​

Стадия кратко

Цель: Построить граф управления потоком и добавить зависимости между RANGE Ключевая концепция: Три типа отношений (вложенные, зависимые, независимые) Эффект: Правильный порядок инструкций

Что делает: Строит граф управления потоком и добавляет зависимости между RANGE.

Зачем это нужно: Операции должны выполняться в корректном порядке. Если загрузка использует значение RANGE, RANGE должен идти первым. Эта стадия отслеживает и обеспечивает эти зависимости.

Паттерн: pm_add_control_flow (bottom-up), которому предшествует второй запуск pm_split_ends

// Analyze which END operations depend on which
END(computation, [RANGE_A]) and END(other_computation, [RANGE_B]) are siblings
→ Creates edge: RANGE_B.src += END(computation)

// Add explicit dependency
RANGE_B waits for RANGE_A to complete

Три типа отношений:

ОтношениеУсловиеЗначение
ВложенныеEND_A — зависимость END_B и RANGE_B — зависимость END_AЦикл A находится внутри цикла B, поэтому A закрывается раньше B
ЗависимыеEND_A — зависимость END_B без такой вложенностиЦикл B должен быть выпущен после цикла A
НезависимыеНи один END не зависит от другогоПорядок свободен; могут выполняться параллельно

Bottom-up обход гарантирует, что зависимости корректно распространяются от листьев к корням.

Svod: schedule/src/linearize/mod.rs, schedule/src/linearize/cfg_context.rs

Стадия 21: Линеаризация​

Стадия кратко

Цель: Преобразовать DAG в линейную последовательность инструкций Ключевой алгоритм: Топологическая сортировка с учётом приоритетов Эффект: Корректный порядок выполнения

Что делает: Преобразует DAG в линейную последовательность инструкций через топологическую сортировку с учётом приоритетов.

Зачем это нужно: Структура графа не задаёт порядок выполнения. Нужно развернуть его в линейную последовательность, соблюдая зависимости. Приоритеты обеспечивают осмысленный порядок (определения до использований, загрузки до вычислений, записи после).

Функция: linearize(sink)

ОперацияПриоритетЗачем
PARAM-20Аргументы ядра (и символические переменные) должны быть определены первыми; при равенстве порядок задаёт слот параметра
BUFFER-18Аллокации первыми
BUFFER (AddrSpace::Local)-17Локальные аллокации сразу после глобальных
END-5Закрывает RANGE
LOAD-1Загрузки до использования
Всё остальное (CONST, ALU, …)0Опускается рядом со своим потребителем
STORE+1Записи после вычислений
RANGE+5RANGE открываются до использования

Меньший приоритет = раньше в последовательности. Это гарантирует:

  • Определения идут первыми
  • Загрузки происходят до вычислений
  • Записи происходят последними
  • RANGE открываются до содержимого, закрываются после

Порядок по run_count: Операции сортируются в первую очередь по частоте выполнения (run_count), затем по приоритету, затем по слоту PARAM и рангу tuplize. Операции с меньшей частотой (вне внутренних циклов) планируются раньше, а операции во внутренних циклах (больший run_count) — позже. Пример: CONST, выполняемый 100 раз, появляется раньше CONST, выполняемого 1M раз.

Вычисление run_count:

run_count = prod(int(r.vmax) + 1 for r in u.in_scope_ranges())

Это вычисляет, сколько раз операция выполняется, исходя из охватывающих её RANGE в области видимости; RANGE, у которого vmax не является конкретным целым, вносит вклад 1.

Svod: linearize() в schedule/src/linearize/linearize.rs

Стадия 22: Чистка IF/ENDIF​

Стадия кратко

Цель: Финальная чистка линейного списка инструкций Ключевая трансформация: Gated STORE → IF/STORE/ENDIF Эффект: Поддержка железа без predicated stores

Что делает: Финальная чистка линейного списка инструкций.

Зачем это нужно: Некоторое железо (современные GPU) поддерживает «predicated stores» — запись в память только при истинном условии. Старое железо — нет. Для такого оборачиваем STORE в IF-блок. Эта стадия нужна только тем бэкендам, у которых нет поддержки predicated store; LLVM, CUDA и Metal обрабатывают gate нативно, поэтому linearize_with_cfg() её не запускает.

Паттерн: line_rewrite_cleanups (через line_rewrite, а не graph_rewrite)

// Gated STORE becomes a conditional store
STORE(INDEX(ptr, idx), value, gate=cond)
→ IF(cond) { STORE(INDEX(ptr, idx), value) } ENDIF

Примечание: Эта стадия использует line_rewrite вместо graph_rewrite, потому что работает с уже линеаризованным списком инструкций, а не с DAG.

На этом этапе список инструкций готов к кодогенерации.
