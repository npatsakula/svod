टेस्टिंग और डिबगिंग

हर tk कर्नेल दो स्तरों पर जाँचा जाता है। Host पर, उसका tile program interpreter में एक सीधे reference के ख़िलाफ़ चलता है, और lowered program हर target के लिए render होता है और, जहाँ toolchain installed हो, compile होता है। tk kernels वाले GPU (CUDA या AMD) पर, lowered कर्नेल interpreter के ख़िलाफ़ या op के अपने graph fallback के ख़िलाफ़ चलता है। Tests IR के hashes नहीं, बल्कि tolerances के भीतर values की तुलना करते हैं।

Interpreter​

interp::run(&program, params, vars) किसी tile program को host पर चलाता है। यह हर parameter के लिए एक Vec<f64> लेता है और run के बाद हर parameter लौटाता है। हर block अपने statements क्रम से चलाता है, और pipeline अपनी serial interleaving के रूप में चलती है। हर value अपने element type में round होती है (interp::round_to), इसलिए नतीजा वही है जो एक सही lowering को accumulation order तक दोहराना चाहिए। Scalar division शून्य की ओर truncate करता है, जैसा emitted code करता है। Runtime variables नाम से bind होते हैं:

let out = run(&prog, vec![a.clone(), b.clone(), vec![0.0; m * n]], &[("b", 1)]).unwrap();

यह interp::Error::{UnboundVar, ParamSize, Division, OutOfBounds} लौटाता है: buffer की capacity से आगे का access एक error है, चुपचाप होने वाला read नहीं। यह threads या barriers को model नहीं करता, इसलिए ordering bugs सिर्फ़ device पर दिखते हैं।

Test फ़ाइलें​

फ़ाइल (test/unit/)स्तरक्या जाँचता है
atoms.rs, layout.rs, layouts.rshostहर atom के operand layouts vendor ISA lane formulas के ख़िलाफ़, F2 algebra के नियम, inference, relayouts और swizzles
build.rs, interp.rs, schedule.rs, sync.rs, emit.rshostBuilder records, interpreter semantics, pipeline expansion, barrier pass, emitted list
ops_plan.rshostहर op का Plan और error, हर shape, dtype और target के लिए
offline.rshostCopy किए गए tune store से पढ़े गए card targets और costs
targets.rshost + deviceहर target के लिए हर kernel family lower, lowering से पहले और बाद में interpret, और compile (ptxas, clang); GPU पर, device gate
probe.rshost + deviceहर cost probe हर target के लिए build होता है; GPU पर, device_costs_are_physical
attention.rs, heads.rs, rows.rs, conv.rs, gather.rshost + deviceProgram एक f64 reference के ख़िलाफ़, फिर lowered कर्नेल program के ख़िलाफ़
device.rs, parts.rsdeviceGEMM शुरू से अंत तक, और वे हिस्से जिनसे attention बनता है (cp.async devices पर)
ops.rsdeviceहर op अपने graph fallback के ख़िलाफ़, बेढब shapes पर
tune.rshost + deviceStore round trip, key की स्थिरता, एक असली GEMM tuning

Suite चलाना​

SVOD_DEVICE device चुनता है। Device tests skipped: … line के साथ सिर्फ़ वहीं skip होते हैं जहाँ चलाने के लिए कुछ नहीं है: SVOD_DEVICE=CPU, ऐसा GPU जिसके लिए tk के पास kernels नहीं, या न SVOD_DEVICE और न कोई supported GPU जुड़ा हुआ। Supported GPU जुड़ा हो और SVOD_DEVICE unset हो, तो वे fail होते हैं और वह मान बताते हैं जो set करना है, क्योंकि जिस suite के सारे device tests skip हों वह pass होकर भी कुछ साबित नहीं करता।

# Host only, no GPU:
SVOD_DEVICE=CPU cargo test -p svod-tk --release --lib
# On the GPU; on a fresh tune store run the cost probes alone first, since the parallel
# suite inflates what they measure and the store keeps the first measurement:
SVOD_DEVICE=CUDA cargo test -p svod-tk --release --lib device_costs_are_physical
SVOD_DEVICE=CUDA cargo test -p svod-tk --release --lib

SVOD_DEVICE=AMD (या AMD:N, KFD node क्रम में) एक AMD GPU चुनता है। कोई target तभी मापा हुआ गिना जाता है जब उस पर families_match_the_interpreter_on_the_device pass हो जाए: device पर हर family का पहला candidate interpreter के ख़िलाफ़। register_staged_families_match_on_cuda AMD data path (register-staged fills, बिना ldmatrix) को CUDA GPU पर चलाता है।

नए GPU पर​

  1. Tune store को किसी ऐसी directory पर रखें जिसे सँभालना है: SVOD_TK_TUNE_DIR=$PWD/tk_tune_$(hostname)।
  2. कई AMD nodes वाली मशीन पर जाँचें कि SVOD_DEVICE=AMD:N जिस node का नाम लेता है वह GPU ही है (/sys/class/kfd/kfd/topology/nodes/*/properties, gfx_target_version)।
  3. पहले device_costs_are_physical अकेले चलाएँ, फिर families_match_the_interpreter_on_the_device, फिर suite। जिस device का gate fail हो उसके आँकड़े रिपोर्ट न करें।

Nemotron के लिए model-level gate (असली weights, generated goldens):

SVOD_DEVICE=CUDA cargo test -p svod-model --release --lib nemotron_diar::parity::half_precision -- --ignored --nocapture --test-threads=1

क्या कर्नेल चला?​

जो op fallback करता है वह CALL की जगह graph ops बनाता है; ops.rs tests नतीजे के ग्राफ़ की calls में कर्नेल का नाम ढूँढते हैं। बिना device के path का अनुमान लगाने के लिए ops::shape planner को बुलाएँ (देखें Op Layer); device पर, planner log बताता है कि op ने ग्राफ़ क्यों लिया (Tuning)।

किसी दूसरे कार्ड के लिए planning​

tk_dump example दिखाता है कि tk ऐसे कार्ड पर क्या चलाएगा जिसका device इस मशीन पर नहीं है: अनुमानित ns के साथ planner की ranking और lattice का हर config क्यों छोड़ा गया (plan.txt), चुने गए config का LLVM text और, जहाँ tools installed हों, उसका PTX, ptxas -v resources और SASS (CUDA) या अपनी resource comments के साथ AMDGCN assembly (AMD), और main loop का एक opcode histogram।

cargo run -p svod-tk --release --example tk_dump -- --card h100-pcie --op gemm --shape 4096x4096x4096
cargo run -p svod-tk --release --example tk_dump -- --arch gfx942 --op attention --shape 8x16x1024x128 --causal --store DIR

--card atoms::CARDS का एक नाम लेता है (rtx3060, h100-pcie, h100-sxm, rtx5070, rtx5090, mi300x, mi355x, rx9070xt, strix-halo); --arch --sms/--xcds के साथ या सूची के पहले कार्ड वाले मानों के साथ एक architecture लेता है। --store कार्ड से copy की गई tune store directory है, जिसकी probe lines ranking की कीमत तय करती हैं; उसके बिना guessed costs यह करती हैं। --cfg N N-वाँ ranked config emit करता है, --out DIR output directory का नाम देता है (tk_dump)।

--op gemm (--shape MxNxK), attention (BxHxTxD), norm (RxD), conv (BxHxWxCINxCOUT) या heads (BxTxHxKVxD) लेता है, हर एक op layer के अपने shape gate और tuning से होकर। --cfg tuned वह config emit करता है जो tuner ने कार्ड पर चुना था, उसे --store copy से पढ़कर और उसमें कुछ लिखे बिना: stored line op, device, dtype, shape और उस config list से match होती है जिससे op layer उसे key करता है, चाहे उसे किसी भी compiler या kernel build ने लिखा हो, और dump पढ़ी गई हर key print करता है या बताता है कि कौन-सी line नहीं है। --compare FILE [--fun NAME] किसी reference kernel (एक .cubin, AMD code object, या SASS, PTX या AMDGCN text) का main loop tk के main loop के बगल में print करता है, उसी तरह गिना हुआ।

cargo run -p svod-tk --release --example tk_dump -- --card rtx3060 --op gemm --shape 4096x4096x4096 --cfg tuned --store ~/.cache/svod/tk_tune
cargo run -p svod-tk --release --example tk_dump -- --card mi300x --op gemm --shape 4096x4096x4096 --compare hk.co --fun NAME

Environment variables​

Variableअसर
SVOD_DEVICEDefault device: CUDA[:N], AMD[:N], CPU। यह तय करता है कि kernels लागू होते हैं या नहीं और कौन से device tests चलते हैं
SVOD_TK_TUNE=0कोई candidate timing नहीं; पहला clean config चलता है (देखें Tuning)
SVOD_TK_TUNE_DIRTune store की directory
RUST_LOG=svod_tk::plan=debugPlanner के फ़ैसले; svod_tk=debug tuner के rounds जोड़ता है
TK_DUMP_LIST=1Program lower होने पर हर emitted instruction छापता है ([i] id op dtype <- sources)। Bodies memoize होती हैं, इसलिए यह हर program की सिर्फ़ पहली lowering छापता है
SVOD_SPEC_DEBUG=1जब कोई program IR spec verification में fail हो, तो ठुकराया गया instruction और उसका tree छापता है

किसी मॉडल की profiling​

Nemotron example एक बार warm up करता है (जिससे tune store भी भर जाता है), फिर दूसरे run को मापता और profile करता है, और उसकी per-kernel report छापता है:

cargo run -p svod-model --release --example nemotron_diarize -- audio_1.wav --dtype bf16 --profile

tk kernels अपने कर्नेल नामों (gemm, conv, flash_attention, heads, layer_norm, …) के तहत graph kernels के बगल में दिखते हैं, उसी तरह मापे हुए।

शांत GPU पर मापें

GPU पर कोई दूसरा process हर आँकड़े को बिगाड़ देता है। Probes और tune store पहले clock को warm करते हैं। Probes को --test-threads=1 के साथ चलाएँ।
