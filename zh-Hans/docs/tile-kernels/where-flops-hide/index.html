FLOPS 藏在哪里

现代 AMD 矩阵核心标榜的那个数字听起来像一纸承诺：规格书写着数千 TFLOPS。你照着写出最显而易见的矩阵乘法（三层嵌套循环，一乘一加），跑一测，却只摸到包装盒上那个数字的百分之几。

FLOPS 并没有凭空蒸发，它们只是藏了起来。把它们找出来，正是任何快矩阵内核都绕不开的功课，无论是编译器生成的（见 概览），还是你用 tk 这样的 tile 库（灵感源自 HipKittens）亲手写的。

本章是本节其余一切的「为什么」：它讲清矩阵核心要全速运转究竟需要什么，以及横在路上的那几个瓶颈。

数学不是瓶颈​

反直觉的地方就在这里。矩阵乘法指令本身（AMD 在 CDNA 上叫它 MFMA，在 RDNA 上叫 WMMA）快得惊人：一条指令就能把两个小 tile 相乘并累加结果。要是你能永远一条接一条地发射这些指令，规格书上的数字就到手了。

但你做不到，因为每两条矩阵指令之间，硬件还得：

  • 算出下一批 tile 的地址，
  • 从远比数学单元慢的内存里把它们取出来，
  • 以矩阵核心要求的确切布局把它们送进寄存器，
  • 而且这一切都得在不让数学单元空等的前提下完成。

Roofline 直觉。 每个内核的上限，要么取决于它算得多快（计算受限），要么取决于它搬数据多快（内存受限）。朴素的 matmul 是内存受限的：时间都耗在等加载上，昂贵的矩阵核心却被饿着。分块的目标就是把内核推向计算受限，让数学单元始终有料可吃。

所以「FLOPS 都去哪了？」这个问题，真正问的是：是什么妨碍了矩阵指令一条接一条地发射？ 答案反复出现的有五个。

五个瓶颈​

这套框架沿用了 HazyResearch 在 ThunderKittens 和 HipKittens 上的工作（见 HipKittens 论文，arXiv:2511.08083）。他们把这套理念从 NVIDIA 移植到 AMD 时发现：tile 与计算这两个抽象可以直接照搬，但真正决定性能的，是围绕内存、调度和芯片布局的那些决策。

1. 布局与地址计算​

矩阵核心要求输入处于特定的寄存器布局，某个特定 lane 持有某个特定元素。数据若以错误布局到达，每次乘法之前你都得付代价把它混洗一遍。而计算该从哪个地址加载（把 tile 坐标换算成 swizzle 缓冲区里的字节偏移），本身就是一笔与数学抢资源的算术。

对策：把 tile 大小定成矩阵核心片段的整数倍，数据一落地就已是 MMA 布局；并把 swizzle 偏移预计算一次，而不是每轮迭代重算。

2. 内存延迟，而且 AMD 没有 cp.async​

在 NVIDIA 上，异步拷贝指令（cp.async，以及后来的 TMA）让你能先发起一次加载，等它落地的同时继续计算——tk 的 CUDA 路径正是为此用上了 cp.async。AMD GPU 没有这些。它转而提供一种直接载入共享内存（LDS）的 buffer load，完全绕开寄存器。快内核会趁矩阵核心啃着当前这块数据时，把下一块数据流进 LDS。这一步搞砸，数学单元每次加载都得停顿。

3. 共享内存的 bank 冲突​

共享内存被切成若干 bank。如果一个 wave 里的两个 lane 在同一周期命中同一个 bank，访问就会串行化，一次内存事务被你拆成了好几次。HipKittens 靠实测逆向出了 CDNA 的 LDS 结构：64 个 bank，分两个相位访问，每相位 32 个 lane。 对策是为 LDS 内部布局精心挑一个 XOR swizzle，让一个 wave 的各 lane 总是散落到不同的 bank 上。tk 直接移植了这些 swizzle。

4. 计算与内存的重叠​

NVIDIA 靠高占用率隐藏延迟：常驻许多 warp，一个停顿了另一个顶上。AMD 矩阵核心内核一般指望不上这一招，于是它们靠交织指令流显式地重叠。两种模式反复出现：

  • 8-wave 乒乓（ping-pong）：一种生产者/消费者划分，一部分 wave 只搬内存、另一部分只做计算，经 LDS 交接。
  • 4-wave 交织（interleave）：把矩阵指令与向量 ALU、指数单元更细粒度地交织起来。

谁胜出取决于工作负载，并非一成不变。

5. 小芯片的线程块排序​

数据中心级 AMD GPU 由若干小芯片（XCD）组成，每个都拥有自己那一片 L2 缓存。如果两个触碰同一份数据的工作组落在不同小芯片上，它们就没法共享缓存。重新映射哪个工作组 ID 在哪里运行，就能让协作的块留在同一小芯片上，白白收回一截实打实的性能。

架构的视角：MFMA、WMMA 与 mma.sync，wave32 与 wave64​

有三个硬件事实塑造了 tk 构建的每一个 tile 内核，值得记牢：

  • CDNA（数据中心，例如 gfx942）经 MFMA 指令发射矩阵乘法，跑 wave64，即每个波前 64 个 lane。
  • RDNA（例如 gfx1151，RDNA3.5，wave32）发射 WMMA 指令，跑 wave32，即 32 个 lane。
  • NVIDIA（sm_80+）发射 mma.sync，跑一个 warp32，即 32 个 lane，但片段布局又是自成一套：一个 16×16 tile 被当作两个 m16n8 半块来持有。

lane 数一变，tile 的元素在 wave 上的分布就跟着变，寄存器布局随之改变，规约也随之改变；而即便宽度相同，片段布局也各不相同。一个为其中一种写、却在另一种上运行、又没把这点考虑进去的内核，会悄无声息地算错。让同一个内核在三者上都正确，自成一章：Wave32 与 Wave64。

面向 GPU 专家

HipKittens 的 analysis/paper_experiments/ 微基准把上述瓶颈逐一量化，为设计提供了依据：

瓶颈发现
瓶颈 3（bank 结构）LDS 微基准证实了 CDNA 上 64 个 bank 分两相位访问、每相位 32 lane，正是 XOR swizzle 所针对调优的结构。
瓶颈 4（重叠并非通用）一个 BF16 GEMM 在 8-wave 乒乓下达到峰值；一个 FP8 GEMM 则在 4-wave 交织下达到峰值。最优的 wave 重叠策略因 dtype 而异。
瓶颈 5（小芯片 swizzle）为 XCD 局部性重映射工作组 ID，可在一个大 GEMM 上带来可观测的加速。

tk 把这些调节杆逐一落地：XOR swizzle 在 tk/src/swizzle.rs（移植自 HipKittens 的共享 tile 布局），L2/小芯片重映射在 tk/src/grid.rs（l2_swizzle）；计算/内存的重叠则表达为 Flash Attention KV 循环上的一个 sched::pipeline(SchedKind::Attention, …) 标记，由线性化之后的一个调度遍来消费。

当这个高层标记还不够用时，AUTHOR 面孔还直接暴露了原始的机器调度器内建函数（以 Op::Custom 形式），用来从瓶颈 4 里再榨出最后几个百分点：

  • 控制 MFMA 突发前后的 wave 发射优先级，
  • 为寄存器分阶段的预取推迟 LDS 等待，
  • 把一簇加载、MFMA、存储钉死在机器调度器面前。

sched::pipeline 是默认方式；上面这些则是手动覆盖，用来亲手摆放调度。

为什么这很重要​

本节余下的一切，都是对这五个瓶颈之一的回应：

  • 下一章 什么是分块 回应瓶颈 1–3：把数据放进正确的布局、正确的内存，且无冲突。
  • Flash Attention 展示瓶颈 2 和 4 的实战：双缓冲流式传输，加一条显式流水线。
  • Wave32 与 Wave64 则是瓶颈 1、lane 数差异，以及各架构片段布局一并强加的那笔可移植性税。

一句话：快 GPU 内核不是「把数学写下来」那么简单。它是数学，再加上一份答案——两条矩阵指令之间的每一个周期都去了哪里。FLOPS 就藏在那里。

编译器不是已经在用矩阵核心了吗？

是的，而这里没有任何说法与之相左。对于图原生内核，BEAM 的 TC 动作会把 matmul 直接映射到 WMMA/MFMA，并照着这同样的几个瓶颈给它分块；编译器完全有能力驱动矩阵核心。这五个瓶颈是每个快内核（无论编译器生成还是手写）都必须跨过的硬件现实，而不是编译器留下的漏洞。

所以 tk 不是一条与之竞争的代码路径。它是 BEAM 表达不出的那类内核所需的工具（概览），而它之所以站得住脚，恰恰因为它没有添加任何额外复杂度：tk 内核发射的就是编译器早已产出的同一套 UOp IR，没有第二个后端、没有单独的工具链、没有新的调试器。你只在想亲手写一个实现时才会动用它，而即便那时，你也仍然待在这一个编译器之内。
