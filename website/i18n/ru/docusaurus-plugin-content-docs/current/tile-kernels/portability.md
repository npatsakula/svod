# Переносимость {#portability}

## Цели {#targets}

`atoms::Target` описывает, что умеет GPU: его атомы матричных ядер, то, как глобальная память
попадает в кольцо разделяемой памяти (`Fill::CpAsync` или `Fill::Staged`), `ldmatrix` и
транспонирующие загрузки, перемещения между лейнами, какие синхронизации являются инструкциями
(`SyncCaps`), занятость, разделяемую память и число SM; подробности — в его rustdoc.
`Target::for_device(&spec)` определяет цель по живому устройству, `Target::for_arch` — по одной
архитектуре (так делают тесты на хосте), а `Target::offline(arch, sms, xcds)` или
`Target::card(name)` описывает карту, которой на этой машине нет.

Цель объявляет, что чип умеет, и никогда — сколько это стоит. Стоимость его примитивов
(`atoms::Costs`) замеряется на устройстве при первом использовании (`probe::costs`) и хранится в
хранилище тюнинга; тесты на хосте её объявляют ([Тюнинг](./tuning#device-costs)). Таблиц
стоимостей по семействам нет. Стоимости доходят до понижения как `Lowering::device` (ориентация,
обмен или круг через память), а до слоя операций — как устройство `Planner` (ранжирование
кандидатов). Замеренные цели и их числа приведены в [Обзоре](./overview#targets).

`ops::supported(device)` истинно, когда `device` — устройство по умолчанию, у его цели есть ядра
tk3 (`config::has_kernels`) и она сообщает число SM; пробы стоимости запускаются при первом
запросе. На любом другом устройстве каждая операция строит свой графовый вариант
(`Fallback::Target`). Тесты на хосте сверяют раскладки операндов каждого атома с формулами
лейнов из документации ISA вендоров, а для каждой цели с ядрами понижают каждое семейство ядер,
интерпретируют его до и после понижения и компилируют через `ptxas` или clang, если они
установлены. «Скомпилировано» не значит «верно на устройстве»: цель считается замеренной, только
когда на её железе проходит `targets::families_match_the_interpreter_on_the_device`.

Без `cp.async` (у AMD нет асинхронного копирования global → LDS) конвейер загружает каждый шаг в
регистры, считает предыдущий шаг и затем пишет регистры в разделяемую память, на одном или двух
слотах. Тот же путь запускается на CUDA в тесте устройства
(`register_staged_families_match_on_cuda`).

## Стратегия {#strategy}

Принятый подход — **одна общая тайловая программа на операцию**. Ядро вроде `kernels/gemm.rs`
пишется один раз над тайловыми значениями и никогда не ветвится по вендору. Для каждой цели
меняются данные, которые выбирают понижение и слой операций:

| Для каждой цели | Где |
|---|---|
| Атомы матричных ядер и их раскладки | `atoms`, `layout/atoms.rs` |
| Механизмы копирования (`cp.async`, `ldmatrix`, заполнение через регистры, транспонирующие загрузки) | Поля `Target`, эмиттер |
| Шаблоны расписания | `schedule::Schedule` |
| Ранжирование кандидатов конфигураций | `ops::config`, по замеренным `Costs` |

Отдельная программа ядра для одного вендора допускается только как ограниченное исключение.

## Не в этом релизе {#not-in-this-release}

| Пункт | Состояние |
|---|---|
| Hopper TMA, mbarrier, производители с warp specialization | Не начато; GEMM и внимание выполняют `wgmma`, питаемый через `cp.async` |
| Blackwell `tcgen05`, тензорная память | Не начато; sm_120 идёт по пути sm_80 |
| CDNA MFMA 32×32, `buffer_load … lds` | Не начато (раскладки 32×32 есть, атома нет) |
| Ping-pong двух бригад вне CDNA | `Target::crews` равно 2 только там, где матричное ядро работает рядом с векторными блоками, а регистровый файл лейна вмещает аккумуляторы двух бригад (CDNA) |
| Apple | Только атомы; ядер нет |
| Свёртка: вариант с подготовкой изображения в разделяемой памяти, depthwise, групповая | Граф |
| fp8/int8, обратный проход внимания | Не начато |
