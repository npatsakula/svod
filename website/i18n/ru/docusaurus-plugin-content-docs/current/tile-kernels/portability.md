# Переносимость {#portability}

## Цели {#targets}

`atoms::Target` — всё, что понижение знает о GPU:

| Поле | Значение |
|---|---|
| `arch` | `GpuArch::{Cuda, Amd, Metal}` |
| `wave` | Лейнов в варпе или волне |
| `mma` | Атомы матричных ядер с раскладками операндов |
| `group_mma` | Атомы матричных инструкций варпгруппы над дескрипторами разделяемой памяти (CUDA sm_90) |
| `cp_async` | Асинхронные копии global → shared (CUDA sm_80+) |
| `ldmatrix` | Коллективные по варпу загрузки фрагментов 8×8 b16 (CUDA sm_75+) |
| `smem_bytes` | Разделяемая память на блок (opt-in лимит, если устройство его сообщает) |
| `sms` | Число SM или CU, если устройство его сообщает |

`Target::for_device(&spec)` определяет цель по живому устройству. `Target::for_arch(arch)`
строит её по одной архитектуре — так делают тесты на хосте. `atoms::sm86()` — цель RTX 3060 с
28 SM.

Цель объявляет, что чип умеет, и никогда — сколько это стоит. Стоимость его примитивов
(`atoms::Costs`: байт разделяемой памяти, потоковый байт, разбросанный элемент, шаг матричного
ядра, softmax-работа одной оценки, итерация, перемещение между лейнами, круг через разделяемую
память, копия регистра, задержка глобальной памяти) замеряется на устройстве при первом
использовании (`probe::costs`) и хранится в tune store; тесты на хосте её объявляют. Таблиц
стоимостей по семействам нет. Стоимости доходят до понижения как `Lowering::costs` (ориентация,
обмен или круг через память), а до слоя операций — как `Planner::device` (ранжирование
кандидатов).

| Цель | Атомы | Заполнение | Таблицы | Состояние |
|---|---|---|---|---|
| CUDA sm_80+ (sm_86) | `mma.sync` m16n8k16, `ldmatrix` | `cp.async`, 2–3 стадии | да | Замерено на RTX 3060 |
| CUDA sm_90 (Hopper) | `mma.sync` m16n8k16, `ldmatrix`; `wgmma` m64nNk16 над дескрипторами shared (GEMM) | `cp.async`, до 227 КБ shared | да | Замерено на H100 PCIe: GEMM 4096³ bf16 433 TFLOP/s на ядре варпгруппы (234 на `mma.sync`; cuBLASLt 524) |
| AMD RDNA4 (gfx1200, gfx1201) | WMMA 16×16×16, 8 значений на лейн | через регистры, 1–2 стадии | да, не замерены | Скомпилировано в code object; не запускалось |
| AMD RDNA3 / RDNA3.5 (gfx1100–1102, gfx1151) | WMMA 16×16×16, реплицированные входы | через регистры, 1–2 стадии | да, не замерены | Скомпилировано в code object; не запускалось |
| AMD CDNA3 / CDNA4 (gfx942, gfx950) | MFMA 16×16×16, wave64 | через регистры, 1–2 стадии | да, не замерены | Скомпилировано для gfx942; не запускалось |
| Apple | simdgroup 8×8×8 | нет | нет | Только атомы |

`ops::supported(device)` истинно там, где есть таблицы конфигураций; на любом другом устройстве
каждая операция строит свой графовый вариант (`Fallback::Target`). Тесты на хосте сверяют
раскладки операндов каждого атома с формулами лейнов из документации ISA вендора, а для каждой
цели с таблицами понижают каждое семейство ядер, интерпретируют его до и после понижения и
компилируют через `ptxas` или clang, если они установлены. «Скомпилировано» не значит «верно на
устройстве»: цель считается замеренной, только когда на её железе проходит
`targets::families_match_the_interpreter_on_the_device`.

Без `cp.async` (у RDNA нет копирования global → LDS) конвейер загружает каждый шаг в регистры,
считает предыдущий шаг и затем пишет регистры в shared-память, на двух слотах. Тот же путь
запускается на CUDA в тесте устройства (`register_staged_families_match_on_cuda`).

## Стратегия {#strategy}

Принятый подход — **одна общая тайловая программа на операцию**. Ядро вроде `kernels/gemm.rs`
пишется один раз над тайловыми значениями и никогда не ветвится по вендору. Для каждой цели
меняются данные, которые выбирают понижение и слой операций:

| Для каждой цели | Где |
|---|---|
| Атомы матричных ядер и их раскладки | `atoms`, `layout/atoms.rs` |
| Механизмы копирования (`cp.async`, `ldmatrix`, поэтапная загрузка через регистры) | Флаги `Target`, эмиттер |
| Шаблоны расписания | `schedule::Schedule` |
| Ранжирование кандидатов конфигураций | `ops::config`, по замеренным `Costs` |

Отдельная программа ядра для одного вендора допускается только как ограниченное исключение.
