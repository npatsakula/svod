# Библиотека ядер {#kernel-library}

Каждое ядро в `svod_tk::kernels` — функция из спецификации в `Program`, обобщённая по 16-битному
типу элемента (`BF16` или `F16`); `gemm` и `nearest` принимают также 8-битные целые (`I8`, точно
накапливаемые в i32: `gemm` записывает f32, `nearest` масштабирует произведения каждой строки на
`x_scale` и `c_scale` строк).

Там, где конфигурацию ядра выбирает планировщик (`gemm`, `conv`, `attention`, `nearest`),
спецификация (`GemmSpec`, `ConvSpec`, `AttnSpec`, `NearestSpec`) — простое описание форм и
опций, а ядро принимает её допущенной с конфигурацией: `fn k<T>(spec: &Admitted<Spec>) -> Program`.
`spec.admitted(&planner, cfg)` возвращает такую спецификацию, если планировщик допускает `cfg`
именно для неё (конфигурация выполнима на цели для задачи, которую задаёт спецификация, и
заявлена на её форме), или причину отказа; `unsafe` `Admitted::assume(spec, cfg)` принимает
конфигурацию без допуска и ничего не проверяет. Допущенная спецификация доступна только для
чтения: она разыменовывается в спецификацию, а `cfg()` возвращает конфигурацию. Остальные ядра
(`heads`, `norm`, `combine`, `split_merge` и выбор, слияние и пересчёт оценок поиска ближайших
соседей) принимают спецификацию как есть, с конфигурацией внутри.

У `GemmSpec`, `ConvSpec`, `AttnSpec`, `HeadsSpec` и `NormSpec` есть `batch: Batch`:
`Batch::Static(n)` запускает `n` батчей, а `Batch::var(name, min, max)` (это `ir::Var`) — живое
количество из переменной времени выполнения, связываемой по имени, с буферами, рассчитанными на
`max`. У `GemmCfg` и `FaCfg` есть `lowering(&device)` (`atoms::Device`: цель и её стоимости);
остальные ядра понижаются с `Lowering::new(&device)`. Модели обращаются к этим ядрам через
[слой операций](./op-layer), который выбирает конфигурацию.

| Ядро | Спецификация → программа | Имя ядра | Операция |
|---|---|---|---|
| GEMM + эпилог | `GemmSpec` → `gemm::gemm` (`TailSpec` → `gemm::gemm_tail` при разбиении хвоста) | `gemm` (+ `split_merge`) | `ops::linear` |
| Свёртка (implicit GEMM) | `ConvSpec` → `conv::conv` (+ `gemm::split_merge` при разбиении) | `conv`, `split_merge` | `ops::conv2d` |
| Flash attention, прямой проход | `AttnSpec` → `attention::attention` | `flash_attention` | `ops::attention` |
| Слияние разбиений | `CombineSpec` → `attention::combine` | `combine_splits` | `ops::attention` с разбиениями |
| Пролог внимания | `HeadsSpec` → `heads::heads` | `heads` | `ops::heads` |
| LayerNorm / RMSNorm | `NormSpec` → `rows::norm` | `layer_norm` / `rms_norm` | `ops::{layer_norm, rms_norm, add_*}` |
| Поиск ближайших соседей | `NearestSpec` → `nearest::nearest` | `nearest` (+ `nearest_select`, `nearest_merge`, `nearest_rescore`) | `ops::{nearest, k_nearest, k_nearest_reranked}` |

## GEMM {#gemm}

`c = scale·act(a·bᵀ + bias) + residual`, где `a [batch·m, k]` и `b [n, k]`. Всё после
матричного произведения выполняется на аккумуляторе f32, а результат округляется один раз при
записи.

| Поле `Epilogue` | Действие |
|---|---|
| `bias` | Строка `[n]`, прибавляемая к аккумулятору (`[2n]` для gated) |
| `act` | `Act::None`, `Act::Gelu` (аппроксимация erf, погрешность не больше 1.5e-7), `Act::Silu` |
| `gated` | `b` имеет форму `[2n, k]`, строки gate над строками up; выход `act(gate)·up` (SwiGLU, GeGLU) |
| `scale` | Умножает активированное значение до прибавления residual |
| `residual` | `[batch·m, n]`, прибавляется последним |
| `out_f32` | Выход и residual в f32, аккумулятор записывается без округления |
| `rope` | `Rope { heads, head_dim, seq }`: первые `heads` голов по `head_dim` столбцов поворачиваются таблицами cos и sin формы `[seq, head_dim/2]` (строка выхода `m` — на позиции `m % seq`), столбцы после них записываются как есть; только вместе со смещением и на тайле, варпы которого держат целые головы (`GemmCfg::turns`) |

`GemmCfg { tile: [bm, bn, bk], warps: [rows, cols], core, schedule, order, tail }`. Строки за `m`
и столбцы за `n` — это view с границами, поэтому `m` и `n` произвольны. `k` обязано быть кратным
`bk`. `core: Core::Group` выпускает произведения на `wgmma` (sm_90);
`schedule: Schedule::ping_pong(k)` запускает две строки варпов в режиме ping-pong над одним слотом
(CDNA). Блоки обходят тайлы выхода группами по `order` строк тайлов (`gemm::TileOrder`, по
умолчанию 8, `TileOrder::DEFAULT`; одна строка — построчный обход, все строки сетки — по
столбцам), так что одновременно резидентные блоки читают одни и те же тайлы B. Планировщик
планирует каждую конфигурацию со значением по умолчанию; конфигурация может нести и другую высоту
группы (поле `g` её кода).

Поворот читает для каждого элемента его парную половину на полголовы дальше через `flip` по
столбцам. Когда столбцы варпа держат целые головы, лейн держит обе половины, и `flip` — это
переименование регистров. Таблицы читаются через периодический view, так что каждая голова
строки читает одну и ту же строку `[head_dim/2]`. В ранжировании поворот не бесплатен: его
операции и чтения таблиц заявляются рядом с операциями эпилога, а тайл, не держащий целых голов,
отвергается.

`tail` (`gemm::TailSplit`, не больше `config::TAIL_SPLITS` частей) разбивает тайлы неполной
последней волны по K: целые волны идут параллельно по данным, хвост пишет частичные суммы в f32, а
`split_merge` применяет эпилог. Планировщик оценивает каждое разбиение со стоимостью запуска
(`config::LAUNCH`) за каждый запуск после первого и отвергает разбиение, частичные суммы которого
превышают восьмую часть памяти устройства (`ShapeRejected::Partials`); тюнер замеряет лидирующее
разбиение рядом с его конвейером без разбиения. Батчевые, gated, поворачивающие и свёрточные GEMM
разбиения не получают.

Таблицы тайлов нет. `config::Planner::gemm_ranked` перебирает тайлы, `bk`, сетки варпов,
глубины кольца и развёртку, оставляет то, что понижение выполняет на цели (атомы замощают сетку
варпов, заполнения делятся на целые 16-байтовые куски на поток, кольцо помещается в разделяемую
память), и ранжирует остальное в наносекундах времени SM по замеренным `Costs` устройства. Все
входные данные ранжирования, относящиеся к устройству, замерены; константы модели (`BAND`,
`OVERLAP_WAVES`, `LAUNCH` и веса операций каждого семейства, каждая помечена `Model:` в
`ops::config`) рассчитаны на то, чтобы быть верными для любого устройства, а байты заполнения
оцениваются по замеренной лестнице кэша. Выход GEMM оценивается в байтах его типа вместе с
чтениями residual и смещения. Ранжирование задаёт порядок, а тюнер замеряет первые 56 тайлов
(`config::SHORTLIST`), которые компилируются без вытеснения регистров ([Тюнинг](./tuning)).

## Свёртка {#convolution}

`conv::conv` — неявный GEMM над channels-last `x [b, h, w, cin]` и `w [cout, kh, kw, cin]`:
A — это view изображения с отображением строк (`conv::im2col_view`), поэтому строки паддинга
читаются как ноль и ничего не материализуется. `K = kh·kw·cin` выполняется одним конвейером, и
каждый шаг лежит внутри одного отвода ядра свёртки (`bk` делит `cin`). На голодающей сетке из
одного статического батча `ConvCfg::split` (поле `split` у `ConvSpec`) разбивает K по оси z
сетки, а `gemm::split_merge` применяет эпилог. `ops::conv2d` выполняет 1×1 как `linear` и
оставляет на графе `groups ≠ 1`, `cin`, не кратное 16, и `cout`, не кратное 8.

## Flash attention {#flash-attention}

`o = softmax(q·kᵀ·scale + bias)·v` над `q [batch, t, heads, d]` в порядке последовательности и
`k`, `v [batch, tk, kv_heads, d]`. Q остаётся в регистрах, а K/V идут потоком через кольцо в
разделяемой памяти. Состояние online softmax `(m, l, o)` переносится в f32 с `exp2`.

| Возможность | Как |
|---|---|
| GQA | Голова запроса `h` читает KV-голову `h / (heads / kv_heads)` |
| Cross attention | `tk ≠ t` — свойство view |
| Любые `t`, `tk` | Границы вместо паддинга: тайл запросов и последний блок ключей — view с границами, а ключи за `tk` маскируются |
| Размерности головы | Любое `d`, которое замощают оба произведения и чьи заполнения делятся на целые куски на поток (`FaCfg::fits`); модели используют 48, 64 и 128 |
| `AttnMask::causal` | Блоки ключей за диагональю пропускаются через число итераций |
| `AttnMask::window` | `(left, right)` вокруг каждого запроса; блоки вне окна пропускаются |
| `AttnMask::chunk` | Блочное внимание: запрос видит свой чанк, `left` чанков до него (все, если граница не задана) и `right` после |
| `AttnMask::key_lens` | `[batch]` i32 — число валидных ключей; блоки за длиной пропускаются |
| `AttnMask::key_mask` | `[batch, tk]` i32 — видимые ключи (шаг строки округлён вверх до 8), читается в каждом блоке |
| `AttnMask::seg_start` | `[batch, t]` i32 — начала сегментов упакованных строк, неубывающие вдоль `t` |
| `AttnMask::bias` | `[batch or 1, heads, t, tk]` — аддитивное смещение в типе потока (шаг строки округлён вверх до 8), прибавляется к масштабированным оценкам до масок |

Предикат вычисляют только блоки ключей, которые пересекает граница causal, окна, чанка, длины
или сегмента; блоки целиком внутри идут без маски. Маска ключей и смещение читаются в каждом
блоке. Запрос, не видящий ни одного ключа, даёт нули — так же, как их пишет граф.

**Режим кэша** (`AttnSpec::cache = Some(CacheLayout { .. })`) читает K и V из кэша
`[rows, tk, heads_total, d]`, который хранит головы нескольких слоёв:

| Поле `CacheLayout` | Действие |
|---|---|
| `rows`, `heads_total` | Форма кэша |
| `row_map` | Параметр `[batch]` i32: строка кэша, которую читает каждая полоса батча |
| `appended` | Строки ключей и значений `[batch, appended, kv_heads, d]`, оцениваемые после закэшированного префикса (токены, только что спроецированные шагом декодера), не больше одного блока ключей; 0 — ничего не добавляется |
| `app_lens` | Параметр `[batch]` i32 — число видимых добавленных строк |

Первая из голов этого внимания задаётся параметром `head_start` формы `[1]` i32, поэтому каждый
слой выполняет одну и ту же программу.

**Упакованный режим** (`AttnSpec::packed`) читает `q`, `k` и `v` из одного параметра
`[batch, t, heads + 2·kv_heads, d]` — слитой проекции — по смещениям голов 0, `heads` и
`heads + kv_heads`, без кэша. Ядро называется `flash_attention_packed` и настраивается отдельно
от ядра с раздельными операндами; на одной конфигурации оба вычисляют одни и те же биты.

**Разбиения по ключам** (`FaCfg::splits > 1`) дают нескольким длинным строкам, например шагу
декодера, больше блоков. Каждое разбиение пишет частичные результаты f32 `o_part`, `m_part` и
`l_part`, а `combine` их сливает. `Attn::splits = Some(n)` фиксирует число разбиений; при `None`
`Planner::splits` предлагает 1, 2, значения около двух блоков на SM и по разбиению на каждый
блок ключей, а тюнер замеряет каждого кандидата с разбиением вместе с его слиянием.

`FaCfg { bq, bkv, schedule, splits, forms, key_warps, warp_rows, core }`:

| Поле | Действие |
|---|---|
| `warp_rows` | Строк запросов на варп: 16 (одна строка атомов) или 32 (каждый фрагмент K и V кормит две строки атомов); форма на 32 строки — вариант, который тюнер замеряет рядом с её тайлом на 16 строк |
| `key_warps` | Блок с одной строкой варпов (`bq = 16`, предлагается при `t ≤ 16`) делит свои блоки ключей между 1, 2 или 4 варпами, у каждого из которых свои слоты кольца и состояние softmax; результаты сливаются через разделяемую память |
| `core` | `Core::Wide` выполняет оба произведения на MFMA 32×32×8 (CDNA); `Core::Group` — на `wgmma` (sm_90) |
| `forms` | Формы softmax, описанные ниже |

Кандидаты берутся из той же решётки и модели стоимости, что и у GEMM
(`Planner::attention_ranked`). Там, где заполнение идёт через регистры, тайл значений хранится
по столбцам, чтобы его фрагменты собирались 16-байтовыми загрузками; на RDNA4 само заполнение —
транспонирующая загрузка (`global_load_tr_b128`).

Softmax принимает новый бегущий максимум, только когда он вырастает более чем на 8 в единицах
log2 (ленивое перемасштабирование FlashAttention-4). Пять `Forms` — ручки тюнера, при
планировании все выключены; тюнер включает каждую там, где замер быстрее (проход по формам,
затем тайлы при этих формах, затем снова формы на победителе):

| Поле `Forms` | Действие |
|---|---|
| `truncate_p` | Вероятности bf16 усекаются, а не округляются, и сумма строки складывает значения как они хранятся |
| `sum_after` | Сумма строки следует за произведением P·V, а не предшествует перемасштабированию |
| `skip_rescale` | Перемасштабирование выхода — это `Scale`, который пропускает каждая волна, чьи строки все сохранили свой максимум |
| `raw_max` | Бегущий максимум остаётся в единицах сырых оценок: умножение на строку, а не на оценку |
| `bias_direct` | Тайл смещения каждого блока ключей читается из глобальной памяти в раскладке оценок, а не через слот кольца |

## Пролог внимания {#attention-prologue}

`heads` разделяет слитую проекцию `qkv [batch, t, (heads + 2·kv_heads)·d]` на тензоры в порядке
последовательности `q [batch, t, heads, d]` и `k`, `v [batch, t, kv_heads, d]`. При желании он
RMS-нормализует `q` и `k` по голове с весами `[d]`, а затем применяет к ним ротационное
позиционное кодирование. Поворот спаривает две половины головы, используя таблицы `(cos, sin)`
формы `[t, d/2]`, общие или по батчу (`Rope { per_batch }`). Блок обрабатывает `br` строк
одного слота головы. `d` должно быть степенью двойки в диапазоне 16..=256, кандидаты —
`br ∈ {4, 8, 16}`.

## Нормализации {#norms}

`rows::norm` использует один варп на строку и слитые редукцию и отображение в f32:

| `Norm` | Формула |
|---|---|
| `Layer` | `(x − mean)·rsqrt(var + eps)·w + b` |
| `Rms` | `x·rsqrt(mean(x²) + eps)·w` |

С `residual: true` ядро нормализует `x + residual`, округлённое до типа элемента, и также
записывает эту сумму — residual-поток pre-norm слоя трансформера. `d` должно быть кратным 256 в
диапазоне 256..=2048, кандидаты — `br ∈ {4, 8, 16}` строк на блок.

## Поиск ближайших соседей {#nearest-neighbour-search}

`nearest::nearest` оценивает строки `x [n, d]` против кандидатов `c [m, d]` по метрике `Metric`
(`SquaredL2`, `ShiftedL2`, `L2`, `NegDot`) и оставляет для каждой строки `k` наименьших оценок по
возрастанию вместе с их индексами. `NearestSpec { n, m, d, dtype, metric, floors, groups, k, live }`
задаёт свой тип элемента (`dtype`: 16-битное число с плавающей точкой или 8-битные целые), и ядро
работает только над этим типом. `NearestCfg::list` (`nearest::Way`) говорит, где хранятся `k`
наименьших оценок строки:

| `Way` | Список |
|---|---|
| `Registers` | Все `k` в регистровом списке |
| `Queued(Pow2)` | Регистровая очередь из стольких оценок (от 2, меньше `k`), сливаемая с остальным списком, который хранится в выходах |
| `Matrix(SelectCfg)` | Оценки записываются матрицей, строки которой составляет в список `nearest_select` |

`Pow2` хранит степень двойки, так что очередь, а также ширина и глубина очередей лейнов списка
(`LaneQueue`) — степени двойки по построению. При разбиении (`NearestCfg::splits > 1`) блоки
одного блока запросов сворачивают каждый свою долю кандидатов, а `nearest_merge` сливает списки
долей. `k_nearest_reranked` ищет по 8-битным или 16-битным строкам и заново оценивает оставленных
кандидатов в f32 с помощью `nearest_rescore`.
