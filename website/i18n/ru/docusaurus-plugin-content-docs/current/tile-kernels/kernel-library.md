# Библиотека ядер {#kernel-library}

Каждое ядро в `svod_tk3::kernels` — функция `fn k<T: Elem>(spec: &Spec) -> Program`, обобщённая
по 16-битному типу элемента (`BF16` или `F16`). У каждой спецификации есть `batch: Batch`:
`Batch::Static(n)` запускает `n` батчей, а `Batch::Var { name, min, max }` — живое количество
из переменной времени выполнения, связываемой по имени, с буферами, рассчитанными на `max`.
У каждого типа конфигурации есть `lowering(&device)` (`atoms::Device`: цель и её стоимости). Модели обращаются к этим ядрам через
[слой операций](./op-layer), который выбирает конфигурацию.

| Ядро | Спецификация → программа | Имя ядра | Операция |
|---|---|---|---|
| GEMM + эпилог | `GemmSpec` → `gemm::gemm` | `gemm` | `ops::linear` |
| Свёртка (implicit GEMM) | `ConvSpec` → `conv::conv` (+ `gemm::split_merge` при разбиении K) | `conv`, `split_merge` | `ops::conv2d` |
| Flash attention, прямой проход | `AttnSpec` → `attention::attention` | `flash_attention` | `ops::attention` |
| Слияние разбиений | `CombineSpec` → `attention::combine` | `combine_splits` | `ops::attention` со `splits` |
| Пролог внимания | `HeadsSpec` → `heads::heads` | `heads` | `ops::heads` |
| LayerNorm / RMSNorm | `NormSpec` → `rows::norm` | `layer_norm` / `rms_norm` | `ops::{layer_norm, rms_norm, add_*}` |

## GEMM {#gemm}

`c = act(a·bᵀ + bias) + residual`, где `a [batch·m, k]` и `b [n, k]`. Всё после матричного
произведения выполняется на аккумуляторе f32, а результат округляется один раз при записи.

| Поле `Epilogue` | Действие |
|---|---|
| `bias` | Строка `[n]`, прибавляемая к аккумулятору (`[2n]` для gated) |
| `act` | `Act::None`, `Act::Gelu` (аппроксимация erf, погрешность не больше 1.5e-7), `Act::Silu` |
| `gated` | `b` имеет форму `[2n, k]`, строки gate над строками up; выход `act(gate)·up` (SwiGLU, GeGLU) |
| `residual` | `[batch·m, n]`, прибавляется последним |

`GemmCfg { tile: [bm, bn, bk], stages, warps: [rows, cols], group_m, unroll }`. Строки за `m`
и столбцы за `n` — это view с границами, поэтому `m` и `n` произвольны. `k` обязано быть
кратным `bk`.

Слой операций не держит таблицы тайлов. `config::Planner::gemm_ranked` перебирает параметры
конструкции (выходные тайлы на 32–256 строк и 48–256 столбцов, `bk` 16–64, девять сеток варпов,
глубины кольца, которые выполняет предвыборка цели, со свёрнутым и развёрнутым циклом), оставляет
то, что понижение может выполнить (атомы замощают сетку варпов, заполнения делятся на целые
16-байтовые куски на поток, кольцо помещается в разделяемую память), и ранжирует остальное в
наносекундах времени SM по замеренным `Costs` устройства. Итерация блока выдаёт работу по трём конвейерам:
операндные фрагменты каждой волны, прочитанные из разделяемой памяти, шаги матричных ядер и
потоковое заполнение, плюс фиксированная стоимость итерации. Конвейеры перекрываются между
волнами, которые держит SIMD: самый длинный оплачивается целиком, остальные — долей в одну на число
волн на SIMD, но не более четырёх (`OVERLAP_WAVES`: шестнадцать волн на SIMD выполняют тайл не
быстрее четырёх на gfx1201 и sm_86). SIMD, держащий меньше волн, чем `step_lone / step` — столько
волн скрывают задержку цепочки матричного ядра, — выполняет шаги во столько же раз медленнее, причём
независимые аккумуляторы волны считаются за волны. Самый занятый SM выдаёт работу
`per_sm = ⌈blocks / sms⌉` блоков, беря следующий по завершении предыдущего, а фиксированная
стоимость итерации делится между блоками, которые он держит одновременно (`resident`, по
разделяемой памяти и оценке регистров); раунд этих блоков — не меньше собственной выдачи одной
волны (блок, в котором волн меньше, чем у SM SIMD'ов, оставляет остальные простаивать), и каждый
раунд сверх своей выдачи платит задержку памяти, которую не скрывает опережение на одну стадию
конвейера:
`cost = trips × (max(per_sm × (body + trip / resident), rounds × simds × (body + trip) / waves) + rounds × latency / (stages − 1))`
при `rounds = ⌈per_sm / resident⌉`, где `body` — перекрытые конвейеры (`Planner::pipelined`). Байт
заполнения оценивается по тому, откуда он приходит: по скорости L2, когда уникальные байты
помещаются в три четверти кэша, по скорости DRAM — когда их больше ещё наполовину, смесью между
ними, и никогда не дороже той доли, которую одновременно выполняющиеся блоки перечитывают из строк
друг друга — строки A своей группы и свои столбцы B (`Planner::fill_byte`). Без
границы по волне ранжирование gfx1151 начиналось с тайлов 256×256 в
один варп, которые шли на 1–3 TFLOP/s. Число регистров раскладки лишь оценивает, сколько блоков
резидентны; оно ничего не допускает, поскольку завышает счёт там, где фрагменты реплицированы
(WMMA gfx11). Ранжирование сохраняет каждый конвейер тайла; [хранилище тюнинга](./tuning)
выбирает среди первых 64 выходных тайлов и сеток варпов, чьи скомпилированные ядра не
вытесняют регистры, каждый — на его первом чистом конвейере (если вытесняют все — первые 64,
которые компилируются), а затем среди остальных конвейеров тайла-победителя. Допускает
компилятор, а выбирает секундомер, потому что модель хорошо упорядочивает тайлы блоков и плохо —
сетки варпов (на sm_86 замеренный лучший вариант оказывался на 92-м месте из 109 тайлов);
конвейеры она ранжирует одна, пока победитель не известен, поэтому развёрнутое кольцо,
которое вытесняет регистры, уступает своему свёрнутому двойнику: на gfx1151 развёрнутые тайлы
внимания 64×16 и 128×16 при d = 128 вытесняют регистры, а свёрнутые компилируются чисто. Gated
вес для модели — это B-тайл шириной `2·bn` и два аккумулятора, поэтому его лидер идёт на половинной
ширине. `Planner` устройства хранит его цель, его замеренные стоимости и уже ранжированные задачи
(операция планирует свою форму при каждом вызове; ранжирование решётки занимает миллисекунду), по
одному планировщику на устройство на процесс.

У модели нет подогнанных констант: каждая стоимость — собственная стоимость устройства,
замеренная пробой. Где ранжирование и замер расходятся, побеждает замер: добавьте форму в
`qwen3_gemm_candidates_probe` и проверьте, какую стоимость ранжирование упускает.

## Flash attention {#flash-attention}

`o = softmax(q·kᵀ·scale)·v` над `q [batch, t, heads, d]` в порядке последовательности и
`k`, `v [batch, tk, kv_heads, d]`. Q остаётся в регистрах, а K/V идут потоком через кольцо в
разделяемой памяти. Состояние online softmax `(m, l, o)` переносится в f32 с `exp2`.

| Возможность | Как |
|---|---|
| GQA | Голова запроса `h` читает KV-голову `h / (heads / kv_heads)` |
| Cross attention | `tk ≠ t` — свойство view |
| Любые `t`, `tk` | Границы вместо паддинга: тайл запросов и последний блок ключей — view с границами, а ключи за `tk` маскируются |
| Размерности головы | 48, 64, 128 |
| `AttnMask::causal` | Блоки ключей за диагональю пропускаются через число итераций |
| `AttnMask::window` | `(left, right)` вокруг каждого запроса; блоки вне окна пропускаются |
| `AttnMask::key_lens` | `[batch]` i32 — число валидных ключей; блоки за длиной пропускаются |
| `AttnMask::key_mask` | `[batch, tk]` i32 — видимые ключи (шаг строки округлён вверх до 8), читается в каждом блоке |
| `AttnMask::seg_start` | `[batch, t]` i32 — начала сегментов упакованных строк, неубывающие вдоль `t` |
| `AttnMask::bias` | `[batch или 1, heads, t, tk]` — аддитивное смещение в типе потока (шаг строки округлён до 8), течёт через собственный слот кольца рядом с K и V (его байты учитываются при допуске так же, как их) и прибавляется к масштабированным оценкам до масок; блок добавленных строк читает свой тайл смещения напрямую |

Маски — работа по классам тайлов. Предикат вычисляют только блоки ключей, которые пересекает
граница causal, окна, длины или сегмента (`select_if` по началу блока); блоки целиком внутри
идут без маски. Bool-маска ключей применяется в каждом блоке. Запрос, не видящий ни одного
ключа, даёт NaN, как softmax над пустой строкой.

**Режим кэша** (`AttnSpec::cache = Some(Cache { .. })`) читает K и V из кэша
`[rows, tk, heads_total, d]`, который хранит головы нескольких слоёв:

| Поле `Cache` | Действие |
|---|---|
| `head_start` | Первая из `kv_heads` голов этого внимания в строке кэша |
| `row_map` | Параметр `[batch]` i32: строка кэша, которую читает каждая полоса батча |
| `appended` | Ключ и значение `[batch, kv_heads, d]`, оцениваемые после закэшированного префикса (токен, только что спроецированный шагом декодера) |

**Разбиения по ключам** (`FaCfg::splits > 1`) дают нескольким длинным строкам, например шагу
декодера, больше блоков. Каждое разбиение пишет частичные результаты f32 `o_part`, `m_part` и
`l_part`, а `combine` их сливает.

`FaCfg { bq, bkv, stages, splits, unroll, .. }` использует один варп на 16 строк запросов.
Кандидаты берутся из той же решётки и модели стоимости, что и у GEMM
(`Planner::attention_ranked`): блоки запросов на 16–128 строк, блоки ключей на 16–128 ключей,
глубины кольца, которые выполняет цель, со свёрнутым и развёрнутым циклом, — ограниченные тем, что
понижается (заполнения делятся на куски на поток, кольцо помещается в разделяемую память), и
ранжированные по стоимости блока ключей (прочитанные фрагменты K и V каждого варпа, оба тайла,
поступающие потоком, шаги матричных ядер, векторная работа softmax на оценку и фиксированная
стоимость итерации) по блокам ключей каждого раунда блоков запросов, причём каждый раунд ограничен
так же, как у GEMM. Оценка регистров — это фрагменты запроса, ключа, оценок, вероятностей и
значений, живые одновременно в скомпилированном цикле; вытесняет ли конфигурация регистры, решает
скомпилированное ядро. Варп за пределами запросов задачи добавляет работу своих строк-паддинга,
поэтому там, где тайлы заполняют устройство, шаг декодера начинается с блоков из одного варпа; там,
где они оставляют SIMD'ы простаивать, варп с паддингом работает на одном из них. Каузальная маска
начисляет каждому блоку запросов его диагональ. Тайл значений хранится по столбцам там, где его
заполнение идёт через регистры (см. [Раскладки и понижение](./layouts-and-lowering#layouts-and-lowering)),
поэтому его фрагменты собираются 16-байтовыми загрузками, как у ключей; на gfx1201 это дало 5–28%
на форму против одной загрузки на ключ у тайла по строкам. На RDNA4 само заполнение — это
транспонирующая загрузка (`global_load_tr_b128`), поэтому его регистры держат отрезки столбцов и
тоже записываются 16-байтовыми векторами.

Шаг softmax делает как можно меньше векторной работы, что важнее всего там, где матричные ядра
делят ALU SIMD'а (RDNA). Строка принимает новый бегущий максимум, только когда он вырастает более
чем на 8 в единицах log2 (ленивое перемасштабирование FlashAttention-4): иначе поправка равна ровно
1, а вероятности остаются ниже 2⁸. Планировщик предлагает каждую конфигурацию в простых формах;
остальные пять (`FaCfg::forms`: `truncate_p`, `skip_rescale`, `raw_max`, `sum_after`, `bias_direct`) — ручки тюнера,
настраиваемые поочерёдно с тайлами (`ops::attention::tune`, через `descend`), поскольку тайл может
компилироваться чисто лишь при некоторых формах: проход по формам на первой конфигурации
ранжирования, которая компилируется чисто, затем выбор тайла и разбиения по ранжированию при
сохранённых формах, затем снова проход по формам на победителе (через хранилище, поэтому дёшево,
если ничего не меняется). Проход по формам — покоординатный спуск: каждая форма один раз, в этом
порядке, тюнинг из двух кандидатов — формы на данный момент против тех же с
переключённой этой формой; переключение сохраняется только там, где замер быстрее (переключение,
вытесняющее регистры, не допускается). Какая форма экономит регистры, нигде не задано правилом:
решает замер. При выключенном тюнинге каждое внимание работает в простых формах. С `truncate_p`
вероятности, хранимые в bf16, усекаются, а не округляются — пара за инструкцию там, где округление
стоит нескольких, — и сумма строки складывает значения как они хранятся, так что нормировка
остаётся несмещённой; цели, округляющие пару одной инструкцией (sm_80+, gfx950), округляют и
суммируют значения f32: лишнее преобразование хранимых значений стоило 3–5% на sm_86. С
`skip_rescale` перемасштабирование выходного аккумулятора — это `Scale`, который пропускает каждая
волна, чьи строки все сохранили свой максимум; оно окупалось везде, где матричные произведения
исполняются на векторных ALU, а рядом с отдельными матричными ядрами — только там, где лэйн полного
тайла держит 64 выходных регистра (sm_86: +4% при d = 128, нейтрально при d = 64 и на 5–7% медленнее
на шаге декодера, чья единственная строка сохраняет обычное умножение). С `raw_max` (окупается на
тайлах RDNA, полных запросов) бегущий максимум остаётся в единицах сырых оценок (положительный
масштаб коммутирует с максимумом; bias сохраняет масштабированную форму), так что масштабируются
лишь два строковых значения, которые берут экспонента и поправка — умножение на строку, а не на
оценку, — ценой умножения на зависимой цепочке шага, которое чувствует единственная волна шага
декодера (3%), но не полный тайл. С `sum_after` сумма строки следует за произведением, а не
предшествует перемасштабированию; усечённые вероятности в любом случае суммируются как хранятся
(скалярное произведение пар bf16, где цель его имеет), округлённые — в f32. После произведения оба
потребителя читают усечённые значения упакованными один раз (gfx1201); до него, на sm_86 с
округлением, этот порядок был на 3% быстрее при d = 128 (24.7 против 24.0 TFLOP/s, 22.4 до этой
работы) и нейтрален при d = 64 и на шаге декодера. С `bias_direct` (переключается только при смещении) тайл смещения
каждого блока ключей читается прямо из глобальной памяти в раскладке оценок, а не течёт через свой
слот кольца рядом с K и V — запланированную форму: на gfx1151, чей аккумулятор держит по столбцу на
лейн и собирает тайл из кольца по два байта, прямые чтения оказались быстрее без каузальной маски
(3.0 против 3.6 мс при d = 64, B 4, H 8, T 2048), а кольцо — быстрее с ней (1.88 против 2.12 мс).
При каузальной маске (или чанках, видящих все
предыдущие) последние блоки запросов, которые оценивают больше всего ключей, запускаются первыми,
так что хвост раунда — его самые короткие блоки. На gfx1201 ленивое перемасштабирование, усечение,
пропуск и сырой `exp2` ниже подняли ядро d = 128 с 90 до 116 TFLOP/s на случайных данных, а
каузальное внимание Qwen3 — с 63 до 77; сырой максимум, скалярное произведение пар и порядок блоков
довели их до 120 и 79, d = 128 causal 96 → 100 и d = 64 105 → 108 (causal 87 → 92), шаг декодера
без изменений. Остаток до 162 TFLOP/s, с которыми шёл бы один лишь WMMA цикла, размазан тонко:
векторная работа — 15%, загрузки, записи, барьеры и адресация — остальное.

Каждая тайловая конфигурация комбинируется с числами разбиений. `Attn::splits = Some(n)`
фиксирует `n`: ранжируются только конфигурации, у которых не меньше `n` блоков ключей, с `n`
(ограниченным наибольшим числом блоков ключей среди конфигураций), так что названное число никогда
не отбрасывается из-за большого блока ключей. При `None` `Planner::splits` предлагает 1, 2,
значения около двух блоков на SM и по разбиению на каждый блок ключей. Оставляются только значения
не больше меньшего из числа блоков ключей и удвоенной цели по SM. Конфигурация без разбиения идёт
первой, а кандидат с разбиением замеряется вместе со своим слиянием.

Замер пропускной способности внимания (B 4, H 8, T 2048, bf16) в TFLOP/s против tk1:

| Случай | tk3 | tk1 |
|---|---|---|
| d 64 | 24.1 | 23.0 |
| d 64 causal | 22.6 | 20.7 |
| d 128 | 22.3 | 22.3 |
| d 128 causal | 20.9 | 16.5 |

Замер декодирования измеряет внимание одного шага декодера Whisper large-v3 в µs. Шаг
декодера Whisper вызывает именно эти ядра:

| Случай | tk3 | tk1 |
|---|---|---|
| Self attention, 200 закэшированных ключей + добавленный | 21.5 | 89.1 |
| Cross attention, 1500 общих ключей | 66.3 | 78.8 (636 без разбиения) |

Открыто: `row_map` декодирования всё ещё исключён из настраиваемой формы (тюнер замеряет на
временных кэшах из одной строки на полосу, где карта читала бы мусорные строки), поэтому
настроенное cross attention может оказаться не самым быстрым со своей картой: на gfx1151
(2026-10-14) оно настроилось на 90 µs против 60 µs без разбиения.

## Пролог внимания {#attention-prologue}

`heads` разделяет слитую проекцию `qkv [batch, t, (heads + 2·kv_heads)·d]` на головы в порядке
последовательности: `q [batch, t, heads, d]` и `k`, `v [batch, t, kv_heads, d]`. При желании он
RMS-нормализует `q` и `k` по голове с весами `[d]`, а затем применяет к ним ротационное
позиционное кодирование. Поворот спаривает две половины головы, используя таблицы `(cos, sin)`
формы `[t, d/2]`, общие или по батчу (`Rope { per_batch }`). Блок обрабатывает `br` строк
одного слота головы. `d` должно быть степенью двойки в диапазоне 16..=256, кандидаты —
`br ∈ {4, 8, 16}`.

## Нормализации {#norms}

`rows::norm` использует один варп на строку и слитые редукцию и отображение в f32:

| `Norm` | Формула |
|---|---|
| `Layer` | `(x − mean)·rsqrt(var + eps)·w + b` |
| `Rms` | `x·rsqrt(mean(x²) + eps)·w` |

С `residual: true` ядро нормализует `x + residual`, округлённое до типа элемента, и также
записывает эту сумму — residual-поток pre-norm слоя трансформера. `d` должно быть степенью
двойки в диапазоне 256..=2048, кандидаты — `br ∈ {4, 8, 16}` строк на блок. Замерено на 92%
пропускной способности памяти на sm_86.
