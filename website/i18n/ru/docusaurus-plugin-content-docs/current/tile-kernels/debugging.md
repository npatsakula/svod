# Отладка и проверка ядер

Написанное руками ядро надёжно ровно настолько, насколько вы способны его проверить. Глава
[Flash Attention](./flash-attention) показала, какого рода ядро стоит писать руками; эта глава — о
том, как прийти к нему доверию. Лицо USE вручает ленивый `Tensor`, который сливается в большой
граф, — это удобно, но место скверное, чтобы спросить «верно ли считает именно это ядро и насколько
оно быстро?». **Лицо DEBUG** в `tk` для того и есть: прогнать одно ядро на конкретных буферах,
прочитать результат обратно, замерить его и доказать, что рефакторинг не изменил поведения.

---

## Прямой диспатч: прогнать одно ядро, прочитать байты

API прямого запуска (`tk/src/launch.rs`) минует планировщик тензоров целиком. Вы даёте ему тело
ядра и реальные входные тензоры; он реализует входы, выделяет выходы, рендерит, компилирует и
отправляет на исполнение, записывая результат в выход, который можно прочитать обратно:

```rust
// The DEBUG face from tk/src/lib.rs. `outs` are written in place.
run_kernel("tile_add", [1, 1, 1], block, &mut [&mut out], &[&input_a, &input_b], build)?;
let values = out.as_vec::<f32>()?;   // read the GPU result straight back
assert_eq!(values, expected);
```

Раз планирование, слияние и отслеживание зависимостей пропущены, замеряете вы *именно своё ядро*, а
не граф, в котором оно случайно оказалось. В этой изоляции и смысл: когда число неверно, хочется
знать, что оно неверно *здесь*, а не где-то в слитом конвейере.

Замечание о пути: пропустить *планировщик* — не значит пропустить *оптимизатор*. `compile` по-прежнему
прогоняет по вашему `SINK` продакшн-функцию `optimize_kernel_with_config` — она применяет к
опущенному руками телу ноль оптимизаций расписания (это и покупает маркер `opts_to_apply: Some(vec![])`),
но всё так же выполняет общие переписывания, нужные любому ядру перед рендером, в том числе опускание
dtype индексов. Так вы получаете корректный код без планировщика. `ArchCaps` берутся из устройства
буферов; GPU, архитектура которого не распознаётся, — это ошибка, и только хостовое устройство
откатывается к `ArchCaps::GFX942`, чтобы `SINK` всё равно собрался.

## Замеры на реальном оборудовании

Для работы над производительностью `CompiledLaunch` (из `compile_kernel`) открывает
аппаратные таймстампы, а не прикидки по wall-clock:

```rust
// Render + compile once …
let launch = compile_kernel("matmul", grid, block, &mut [&mut c], &[&a, &b], build)?;
// … then dispatch in a loop, outside the timed region.
// SAFETY: the bound buffers stay allocated for `launch`'s lifetime.
unsafe { launch.dispatch(true) }?;
let ns = launch.dispatch_gpu_ns()?;   // Option<u64>: device-measured dispatch time
```

`dispatch_gpu_ns()` один раз диспатчит ядро через профилирующий контекст и читает вокруг диспатча
собственные счётчики таймстампов устройства, так что замеряете вы время на устройстве, а не задержку
прогона туда-обратно при запуске; на бэкенде, который ничего не ставит, результат — `None`. Именно
этим примитивом [автотюнер](./tuning) ранжирует кандидатов, предварительно подняв частоту тем же
`warm_clock`, что и бенчмарки. Criterion-бенчмарки добираются до тех же таймстампов уровнем выше,
через `plan.profile`; см. [Профилирование и бенчмаркинг](./profiling).

## Тесты без GPU и тесты с ним

Сборка `SINK` — это чистое построение UOp-ов, и устройство для неё не нужно; оно нужно лишь для
исполнения. Тестовый модуль (`tk/src/test/unit/`) везде опирается на это разделение, и новое ядро
должно поступать так же:

- **Тесты формы графа** запускаются при каждом `cargo test`. Соберите ядро на буферах-заглушках
  (`UOp::new_buffer(DeviceSpec::Cpu, size, dtype)`, `ArchCaps::GFX942`), отсортируйте `SINK`
  топологически и проверьте, что в нём есть и чего нет: `guide.rs` проверяет, что ядро tile-add
  создаёт `Op::Special`, содержит один `Binary(Add)` и не содержит ни `Wmma`, ни буфера `Local`.
- **Аппаратные тесты** помечены `#[ignore]` и сами пропускаются на неподдерживаемом устройстве:

```bash
SVOD_DEVICE=AMD:0  cargo test -p svod-tk --lib guide::test_tile_add_amd -- --ignored
SVOD_DEVICE=CUDA:0 cargo test -p svod-tk --lib fa::test_fa_graph_check -- --ignored --nocapture
```

Проверки лежат в `tk/src/test/unit/mod.rs`: `device_supported(archs)` для `ArchSet` ядра,
`fragment_device()` для всего, что требует раскладок матричного ядра, `is_cdna_device()` и
`wave32_fragment_device()` для проверок, завязанных на раскладку. Каждая из них также вызывает
`svod_tk::tune::set_enabled(false)`, чтобы численный тест не тюнил каждую затронутую форму.

Для графово-нативного ядра `svod_tensor::custom_kernel_check!` генерирует сравнение целиком:
случайные входы одной формы и dtype, тестируемое ядро, замыкание-эталон, оба результата приводятся к
f32 и сравниваются при `atol = rtol = tol`.

```rust
svod_tensor::custom_kernel_check! {
    test_fa_graph_check,
    inputs (q, k, v): shape [1, 128, 2, 64], dtype svod_dtype::DType::BFloat16,
    run: |q, k, v| {
        let out = crate::kernels::fa::flash_attention(q, k, v).expect("FA build");
        Ok::<_, crate::LaunchError>(out.expect("the FA kernel applies to [1, 128, 2, 64] bf16 on every supported arch"))
    },
    reference: fa_causal_reference,
    tol: 2e-2,
}
```

Отказ ядра (`Ok(None)`) здесь громко валит тест, а не сравнивает эталон сам с собой.

## Отпечатки: доказать, что рефакторинг сохраняет поведение

Тонкий риск с написанными руками ядрами: вы «прибираетесь» в коде билдера, ядро по-прежнему
компилируется и по-прежнему выдаёт правдоподобные числа, но *сгенерированный IR* изменился так, что
проявится лишь позже — на какой-нибудь форме или архитектуре.

От этого защищает `KernelFingerprint` (`tk/src/fingerprint.rs`). LLVM-рендер не детерминирован от
запуска к запуску (ID узлов просачиваются в SSA-имена), а *граф* детерминирован: каждый UOp несёт
рекурсивный структурный `content_hash`, и отпечаток — это такой хеш `SINK` вместе с не зависящей от
порядка свёрткой тегов узлов: `u128` `digest`, плюс `op_counts` и `node_count` для читаемого диффа.

```rust
let fp = kernel_fingerprint(&sink);
assert_eq!(fp.digest, GOLDEN_MATMUL_DIGEST);  // structure unchanged ⇒ behavior unchanged
```

Если отпечаток сдвинулся, значит, вы изменили выдаваемый IR — намеренно или нет, — и золотой тест
заставит вас в это заглянуть. `tk/src/test/unit/golden.rs` так фиксирует билдеры matmul и
flash attention (causal, non-causal, с маской); при падении тест печатает новый дайджест для вставки,
а намеренная смена эталона доказывается дампом и диффом обоих графов. Те же дайджесты служат ключами
дискового хранилища [автотюнера](./tuning), так что изменение ядра заново замеряет его тайлы.

## Ошибки, которые не дают ошибок

Tile-ядро — это граф зависимостей, и пропущенное ребро даёт неверный ответ, а не ошибку компиляции.
Вот те, что уже ловил набор тестов:

| Симптом | Причина | Исправление |
|---|---|---|
| Аккумулятор переносит устаревшее состояние между итерациями цикла | переинициализация на каждой итерации (`g.zero(acc)`) не зависит от счётчика цикла и выносится над циклом | `g.zero(lp.reinit(acc))` |
| Тайл, переносимый циклом, после цикла читает значение до цикла | финальное чтение не упорядочено после `END` цикла | `acc.after(&lp.close())` или `lp.close_carry(acc)` |
| `finish` срабатывает на debug-assert, или линеаризатор неверно ограничивает цикл | две записи закрывают (`END`) один и тот же `RANGE` | одна закрывающая запись на цикл; остальные цепляйте к ней |
| Не те буферы, хотя их число верное | порядок `gl` / `bind_abi` отличается от порядка запуска `[outs..., ins...]` | сначала объявляйте выходы, затем входы в порядке запуска, необязательные буферы — в конце |
| Ядро молча читает не тот поток K/V | `k`/`v` привязаны к форме `q` с другим dtype той же ширины (`Kernel::gl` проверяет только ширину в байтах) | проверяйте dtype в `validate`, как это делает `flash_attention_with` |
| Верно на CDNA, мусор на RDNA | захардкожено число лейнов или константа фрагмента | читайте `caps.wave_size` и `ker.frag(role)` ([Лэйауты и ширина волны](./wave-portability)) |

Те, что *дают* ошибку, — это assert-ы билдера: размер тайла, не кратный его фрагменту; `k_step`, не
кратный K-грани матричного ядра; блок, не составленный из целых волн; многоволновая группа, вызывающая
одноволновую операцию; `ker.frag` на архитектуре без раскладок. Каждый называет неверное значение.

## Какой инструмент под какой вопрос

| Вы спрашиваете… | Используйте |
|----------------|-----|
| «Выдаёт ли этот билдер то, что я думаю?» | тест формы графа по топологической сортировке `SINK` |
| «Выдаёт ли это ядро правильные числа?» | `run_kernel` + `as_vec` или `custom_kernel_check!` против эталона |
| «Насколько оно быстро на этом GPU?» | `compile_kernel` + `dispatch_gpu_ns` |
| «Изменил ли мой рефакторинг выдаваемый IR?» | золотой тест `KernelFingerprint` |
| «Какой тайл выбрал тюнер и почему?» | файл хранилища в `SVOD_TK_TUNE_DIR` ([Автотюнинг](./tuning)) |
| «Не сбоит ли *слой устройства/драйвера*?» | [AMD-бэкенд → Отладка](../backends/amd/debugging), [CUDA-бэкенд → Отладка](../backends/cuda/debugging) |

Последняя строка важна: эта глава — про отладку *ядер*, того IR, что вы написали, и чисел, которые
он выдаёт. Когда проблема лежит ниже — диспатч очереди, сбои памяти, драйвер, PTX JIT, — правильное
место для неё это главы по бэкендам: [AMD](../backends/amd/debugging) и
[CUDA](../backends/cuda/debugging).

---

## Почему это важно

Авторство руками меняет страховочную сеть оптимизатора на контроль. Лицо DEBUG — это способ
совершить этот обмен безопасно: изоляция, чтобы локализовать баги корректности, аппаратные
таймстампы, чтобы делать защитимые заявления о производительности, и структурные отпечатки, чтобы
«я просто прибрался в коде» не могло молча обернуться «я изменил ядро». С этими тремя написанное
руками ядро так же проверяемо, как и автотюненное.
