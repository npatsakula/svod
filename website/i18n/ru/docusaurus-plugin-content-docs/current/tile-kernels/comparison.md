# Три способа написать tile-ядро

Абстракцию тайлов `tk` не изобрёл. Он стоит в небольшом семействе tile-ориентированных систем для
ядер, и понять его устройство проще всего, поставив рядом с двумя ближайшими соседями:

- **[HipKittens](https://github.com/HazyResearch/HipKittens)** — C++ tile-библиотека HazyResearch
  под матричные ядра AMD, прямое происхождение абстракций `tk`.
- **[CuTile](https://github.com/NVIDIA/cutile-rs)** (cutile-rs) — Rust-система NVIDIA Research для
  tile-ядер на GPU NVIDIA.

Все три держатся на ключевой идее из [Что такое тайлинг](./tiling): затянуть в регистры тайлы
размером с фрагмент, посчитать над ними, записать обратно. Различаются они в том, *кто управляет
отображением на оборудование*, — и это различие представляет собой спектр.

---

## Спектр: явный контроль ↔ абстракция под управлением компилятора

Эти три системы стоят на одной оси. На одном конце вы сами распоряжаетесь регистрами, разделяемой
памятью и планированием инструкций; на другом — вы пишете код на уровне тайлов, а нижестоящий
компилятор сам решает, как тот отобразится на потоки, разделяемую память и матричные инструкции.
HipKittens стоит на явном конце, CuTile — на конце, где управление берёт на себя компилятор. `tk` стоит левее центра: явные регистровые
и разделяемые тайлы он даёт, как HipKittens, но вместо самостоятельного бэкенда опускается в единый
UOp IR Svod.

## Бок о бок

| Ось | **tk** | **HipKittens** | **CuTile** |
|------|--------|----------------|------------|
| **Поверхность авторства** | Rust *builder API* (`Kernel`/`Group` создают UOp-ы) | C++ *шаблоны* | Rust *макро-DSL* — пишете обычный Rust в `#[cutile::module]`, макрос захватывает AST |
| **Целевой IR** | **один UOp IR** Svod — тот же, что у всего компилятора | нет (шаблоны → clang amdgcn) | *отдельный* MLIR-диалект `cuda_tile`, сериализуемый в байт-код Tile IR |
| **Опускание** | рендер Svod → LLVM → AMD-бинарник либо → PTX (ассемблируется в cubin через `ptxas`, иначе JIT драйвером), либо → MSL | clang | байт-код → внешний ассемблер `tileiras` → cubin (JIT при первом запуске) |
| **Модель памяти** | **явные** регистровые *и* разделяемые тайлы | явные регистровые *и* разделяемые тайлы | **один** тип тайла (резидентный в регистрах); размещение в разделяемой памяти неявно, его выбирает компилятор |
| **API матричного блока** | явная операция `WMMA` + фрагменты на основе ролей | типизированные тайлы → `__builtin_amdgcn_mfma_*` | единый функциональный интринсик `mma()` |
| **Перекрытие вычислений/памяти** | маркер `sched::pipeline` + проход кодогенерации | руками под каждое ядро (сырые интринсики планирования) | делегировано `tileiras` |
| **Главное отличие** | один IR ⇒ ядра руками и автотюненные ядра на равных | «построено от оборудования вверх» | безопасность памяти через границу запуска |
| **Целевая платформа** | AMD CDNA3 / RDNA3 / RDNA4, NVIDIA `sm_80+`, Apple7+ | AMD CDNA / RDNA | только NVIDIA `sm_80+` |

Поверх этого каждое ядро `tk` объявляет свой собственный набор архитектур: flash attention и
квадратный `matmul` работают на всех семействах, `gemm_nt` и нормализации — на RDNA и CUDA,
single-query attention — на AMD и CUDA, k-means и k-NN — на AMD; полная матрица — в главе
[Библиотека ядер](./kernel-library).

## Как выглядит код

По ощущениям от работы поверхности авторства и вправду разные. Фрагменты HipKittens и CuTile
иллюстративны — они передают *форму* каждой модели, а не точный API; фрагмент `tk` — настоящий API.

**HipKittens** — C++-шаблоны; вы называете тайлы и вызываете умножение напрямую:

```cpp
using namespace kittens;
rt_bf<64, 32>      a, b;     // register tiles of bf16
rt_fl<64, 32, col> acc;      // fp32 accumulator, col layout (MFMA output)

load(a, a_global, {row, k});
load(b, b_global, {k, col});
mma_ABt(acc, a, b, acc);     // acc += a · bᵀ  → __builtin_amdgcn_mfma_*
```

**CuTile** — пишете обычный Rust внутри модуля, который захватывает макрос; тайлы неизменяемы,
разделяемую память компилятор размещает за вас:

```rust
#[cutile::module]
mod kernels {
    use cutile::core::*;
    pub fn gemm(a: &Tensor<f32, A>, b: &Tensor<f32, B>, c: &mut Tensor<f32, C>) {
        let (i, j) = (tile_block_id_x(), tile_block_id_y());
        let mut acc = Tile::<f32, ACC>::zeros();
        for k in 0..a.dim(1) / BK {
            acc = mma(a.partition(AK).load([i, k]),
                      b.partition(BK).load([k, j]),
                      acc);            // one functional intrinsic
        }
        c.partition(CC).store([i, j], acc);
    }
}
```

**tk** — Rust-билдер, который создаёт IR; вы запрашиваете фрагменты по роли и выдаёте операции
`Group` (однобуферная полоса `gemm_core` из `tk/src/kernels/gemm.rs`, в сжатом виде):

```rust
let (outs, ins) = ker.bind_abi(&[GlSpec::new(&[1, 1, n, n], DType::Float32)], &[a_spec, b_spec]);
let g = ker.group_2d(cfg.warps_m, cfg.warps_n);
let a_smem = ker.shared_sw((cfg.block_m, k_step), bf16, TileLayout::Row);   // swizzled LDS strip
let acc = g.zero(ker.acc((reg_m, reg_n), TileLayout::Col));                 // role, not a hardcoded shape

let lp = ker.loop_static(trips);
let a_f = g.fill_local_nobar(a_smem, a_gl, &a_idx, 2);                      // global → LDS, collaborative
let a_sub = g.load(ker.operand((reg_m, k_step), bf16, TileLayout::Row),    // LDS → registers
                   a_f.subtile((reg_m, k_step), (warp_row, 0)), MoveIdx::default());
let acc = g.mma_ab(acc, &a_sub, &bb);                                      // → WMMA UOp
let ended = lp.close();
let _ = g.store(c_gl, acc.after(&ended), MoveIdx::block((0, 0, mrow, nidx), 2));
ker.finish(1)                                                               // SINK { opts_to_apply: Some(vec![]) }
```

Пример CuTile читается как обычная программа; пример `tk` — как сборка графа. В этом и обмен: макрос
CuTile захватывает ваш *синтаксис* и заново его парсит, тогда как `tk` — это библиотека, чьи вызовы
методов *и есть* построение IR.

## Главное концептуальное различие

Два различия важнее всех прочих.

**Кто владеет разделяемой памятью.** У CuTile есть ровно *одна* концепция тайла — регистровый тайл —
и размещение в разделяемой памяти он намеренно прячет; его ассемблер `tileiras` сам решает, как
данные текут через LDS, кеши и матричные блоки. `tk` и HipKittens открывают *обе* — и регистровые, и
разделяемые тайлы — и заставляют размещать данные явно. CuTile сидит уровнем *выше* различия
регистр/разделяемая память; `tk` сидит *на* нём. В этом и цена, и сила контроля: управлять придётся
большим, зато [решения о перекрытии и свизле](./where-flops-hide), на которых добывается
производительность, остаются за вами.

**Где живёт IR.** Вот настоящий отличительный ход `tk`. HipKittens — самостоятельный C++-фреймворк:
он производит ядра, и точка. CuTile опускается в *отдельный* MLIR-диалект, который потребляет лишь
его собственный тулчейн. `tk` опускается в **тот же UOp IR, на котором уже говорит остальной Svod**.
`tk`-ядро — это не артефакт, передаваемый другому компилятору, это подграф в одном IR, рядом с каждым
автотюненным ядром.

:::tip[Для экспертов по GPU]
Различие в целевом IR ощутимо на уровне тулчейна. `tk` рендерит свой `SINK` через `svod-codegen` в
LLVM IR, а затем в AMD-бинарник либо в PTX (ассемблируется через `ptxas`, иначе JIT-ится драйвером),
либо в MSL на Metal — тем же путём, что и графовые ядра. CuTile же сериализует свой tile-диалект в байт-код, который
*внешний* ассемблер `tileiras` превращает в cubin с JIT-компиляцией
при первом запуске; HipKittens — это C++-шаблоны, компилируемые clang. Так что «один IR» для `tk`
буквально означает один пайплайн рендера и компиляции, тогда как остальные перекидывают мост в
отдельный компилятор.
:::

## Почему это важно

Именно это позволяет Svod предложить две вещи, которые обычно взаимоисключают друг друга: дать
компилятору найти расписание — и написать расписание самому, без второго компилятора.

Автотюненный BEAM matmul и написанный руками Flash Attention — оба просто `SINK` UOp-ы в одном DAG.
Они рендерятся одним рендерером, исполняются на одной среде выполнения и печатаются одним отладчиком.
Различает их единственное — маркер `opts_to_apply`, чей дом в главе [Пишем прямо в IR](./lowering):
один и тот же IR несёт и ядро, ведомое оптимизатором, и ядро, ведомое руками.

HipKittens доказывает, что можно сравняться с вендорскими библиотеками, идя от оборудования вверх.
CuTile доказывает, что GPU-ядра можно сделать безопасными и высокоуровневыми. Ставка `tk` уже и для
Svod полезнее: взять tile-модель «от оборудования вверх» и вместо нового бэкенда вокруг неё *говорить
на IR, который у компилятора уже есть*. Вот вся причина, почему `tk` мал, — и причина, почему
написанное руками ядро ощущается полноценным участником, а не костылём.
