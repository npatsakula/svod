# Происхождение ядер

Строка профиля «`r_128_3_32_4_2_2_2_4_4_192_2` — 100 мс» описывает форму ядра, но не
отвечает, чьё это ядро. На второй вопрос отвечает происхождение (origin): каждое запущенное
ядро знает путь модуля, место вызова или узел ONNX, для которого его построили, а профайлер
сводит время по этому пути — по слоям, по блокам, по стадиям.

Эта страница — руководство пользователя: как включить, как разметить модель и как читать
вывод. Сам механизм (поле на каждом узле, входящее в hash-consing и снимаемое снова на
разрезе на ядра) кратко описан в конце, а подробно — на страницах [дизайна IR](./ir-design.md) и
[бестиария операций](./op-bestiary.md).

---

## Как включить {#turning-it-on}

По умолчанию захват выключен и в выключенном состоянии не стоит ничего: узлы не несут
происхождения, а хеши байт в байт совпадают со сборкой без этой возможности. Два
переключателя:

| Переключатель | Эффект |
|--------|--------|
| `SVOD_ORIGIN=1` | захват включён для каждого потока процесса (не задано, пусто или `0` — выключен) |
| `SVOD_ORIGIN_DEPTH=<n>` | сводки оставляют первые `n` сегментов пути (не задано или `0` — полный путь, выводится как `depth leaf`) |

```bash
SVOD_DEVICE=AMD:0 SVOD_ORIGIN=1 cargo run --release -p svod-model --example gigaam_infer -- \
    audio.wav --profile --origin-depth 3 --profile-json profile.json
```

`--origin-depth` имеет приоритет над `SVOD_ORIGIN_DEPTH`; у примера Whisper есть только
`--profile`.

В тестах переключайте захват только для текущего потока, чтобы параллельные тесты сохраняли
идентичность своих графов:

```rust
let _capture = svod_ir::origin::capture_for_thread(true); // restored on drop
```

## Откуда берётся происхождение {#where-origins-come-from}

Происхождение — это путь из кадров, корень первым. Кадр бывает одного из следующих видов:

| Кадр | Отображается как | Кем открывается |
|-------|-------------|-----------|
| `Module` | `encoder.layers.3.ffn1` | код модели, по одному сегменту на модуль (`OriginScope::module`) |
| `Label` | `vad`, `GigaAmCtcJit`, `initializer` | стадии пайплайна, каждая сборка `jit_wrapper!`, импортёр ONNX |
| `Onnx` | `/encoder/Conv` или `#12:MatMul` | импортёр ONNX, по одному на узел: имя узла или `#index:op_type`, если имени нет |
| `Call` | `@ linear model/src/gigaam/encoder.rs:43` | каждая публичная операция `Tensor`, через `origin_call!` на входе |

Именованные кадры соединяются через `.`; кадр `Call` идёт после пробела. Это плоский слой
«файл:строка» под путём модуля: операция открывает его, только если текущий кадр ещё не
является вызовом (побеждает самый внешний), поэтому операция, собранная поверх других
операций (`linear` поверх `matmul`), запишет строку пользователя один раз и никогда —
собственный исходник svod. Слои модулей выше добавляет уже код модели.

### Разметка Rust-модели {#instrumenting-a-rust-model}

В `forward` открывайте скоуп на каждый модуль — с тем же именем, каким записали бы его
префикс в state-dict. В крейте модели есть помощники ровно для этого:

```rust
use crate::state::{scoped, scoped_index};

fn forward(&self, x: &Tensor) -> Result<Tensor> {
    let x = scoped("subsampling", || self.subsampling.forward(x))?;
    let mut x = x;
    for (i, layer) in self.layers.iter().enumerate() {
        x = scoped_index("layers", i, || layer.forward(&x))?;   // layers.0, layers.1, …
    }
    scoped("final_norm", || self.final_norm.forward(&x))
}
```

`scoped` открывает `OriginScope::module(name)` вокруг замыкания; `scoped_index` форматирует
сегмент `name.i` только при включённом захвате; `scope_index(name, i)` делает то же самое в
виде guard-объекта для тел циклов, которые нельзя сделать замыканиями. Каждый модуль
открывает только свой сегмент; вложенность восстанавливает полный путь, так что путь в
профиле совпадает с префиксом ключа state-dict для весов, которых он касался. GigaAM и
Whisper размечены именно так, а `model/src/test/unit/origin.rs` проверяет, что оба набора
путей совпадают.

Стадии пайплайна — корневой сегмент. GigaAM оборачивает сборку JIT в скоуп модуля, пайплайн
`arch` использует метку — так или иначе имя стадии стоит в начале каждого пути, созданного
внутри:

```rust
scoped("ctc_head", || jit.prepare_with_config(mel_spec, lengths_spec, &config))?;

let _stage = OriginScope::label(self.profile_label());   // "vad"
self.vad.probs(waveform)?;
```

Макрос `jit_wrapper!` открывает `OriginScope::label("<WrapperName>")` вокруг каждого
замыкания сборки — отсюда и берётся сегмент `GigaAmCtcJit` ниже. Всё, что построено вне
скоупа, попадает в строку `<unattributed>`.

### Графы ONNX {#onnx-graphs}

Ничего делать не нужно. Импортёр открывает по одному кадру `Onnx` на узел (индекс, имя, тип
операции, домен, opset) и `Label` для каждой ветки подграфа (`then_branch`, `else_branch`)
под узлом, которому она принадлежит, так что тело `If` читается как
`#7:If.then_branch.#0:Add`. Инициализаторы и входы графа находятся под `initializer` и
`input` — но только если они строят вычисляемый узел: литералы и буферы никогда не несут
происхождения.

### Рукописные ядра {#hand-written-kernels}

Ядро `tk` атрибутируется скоупом, активным в момент его сборки, — то же правило, что и для
ядра графа. Планировщик никогда не видит его тело, поэтому `UOp::custom_kernel` собирает и
снимает происхождение при конструировании (`ir/src/uop/constructors/graph.rs`); два слоя,
запускающие одно и то же рукописное ядро, по-прежнему разделяют одну скомпилированную
программу. Входы, которые оно копирует, наследуют происхождение своего производителя.

## Как читать вывод {#reading-the-output}

При включённом захвате `--profile` печатает обычную таблицу по ядрам, а затем две сводки.
Пример — энкодер GigaAM v3, f16, одно окно 60 с на gfx1151, глубина 3:

```
519 dispatches (519 GPU-stamped), total 444.237 ms
  total ms  count    mean µs      %  name
   103.183     16     6448.9   23.2  r_128_3_32_4_2_2_2_4_4_192_2n1
   100.305     16     6269.1   22.6  r_128_3_32_4_2_2_2_4_4_192_2
    80.530     32     2516.6   18.1  r_128_12_32_4_2_2_2_4_4_48_2
    …
origin rollup (depth 3, exclusive; rows sum to the total):
  total ms  count    mean µs      %  origin path
    27.833     32      869.8    6.3  ctc_head.GigaAmCtcJit.layers.3
    27.678     32      864.9    6.2  ctc_head.GigaAmCtcJit.layers.9
    27.620     32      863.1    6.2  ctc_head.GigaAmCtcJit.layers.0
    …
    23.334      2    11666.8    5.3  ctc_head.GigaAmCtcJit.subsampling
     0.661      4      165.2    0.1  ctc_head.GigaAmCtcJit.head
     0.131      1      131.0    0.0  ctc_head.GigaAmCtcJit
origin rollup (depth 3, inclusive; parents contain children, rows overlap):
  total ms  count    mean µs      %  origin path
   444.237    519      855.9  100.0  ctc_head
   444.237    519      855.9  100.0  ctc_head.GigaAmCtcJit
    27.833     32      869.8    6.3  ctc_head.GigaAmCtcJit.layers.3
    …
```

Как это читать:

- **Exclusive** (исключающая сводка) относит каждый запуск ровно один раз — к его
  *основному* происхождению: скоупу, который произвёл значение, записываемое ядром (или,
  если у этого значения происхождения нет, к ближайшему атрибутированному узлу под корнем).
  Строки разбивают итог на части, поэтому шестнадцать строк `layers.N` плюс `subsampling`,
  `head` и остаточная строка `GigaAmCtcJit` дают в сумме 519 запусков и 444 мс. Шестнадцать
  слоёв по 32 запуска — это весь энкодер; разброс по слоям (от 25,3 до 27,8 мс) реален, и
  именно на него стоит смотреть в первую очередь. Если исключающих строк меньше двенадцати,
  каждая строка дополнительно перечисляет свои три главных ядра строками `· name`.
- **Inclusive** (включающая сводка) относит запуск к каждому предку каждого происхождения,
  слитого в ядро. Родительская строка содержит дочерние, поэтому `ctc_head` — это 100 %, и
  строки перекрываются. Она показывает, сколько времени блока прячется в ядрах, слитых
  через границы модулей.
- **Глубина** — число сохраняемых сегментов пути. Глубина 3 даёт здесь строки по слоям;
  глубина 4 разбивает слой на `ffn1`, `mhsa`, `conv`, `ffn2`, `final_norm`; leaf сохраняет
  полный путь. Кадры `Call` никогда не становятся ключами сводки — это детали в строках
  ядер и в JSON.
- Ядро, сливающее два модуля, в исключающей сводке относится к тому, чьё значение оно
  записывает (остаточное сложение попадает на слой, а не на `ffn2`), а во включающей — к
  обоим.

Любой `RunProfile` несёт обе сводки: `render_report()` (раскладка выше, используется
`gigaam_infer`) и `render_table()` (`--profile` у Whisper, другая таблица ядер) добавляют
одинаковый раздел происхождения, обрезанный на той глубине, с которой профиль был
получен; `render_report_at(d)` / `render_table_at(d)` / `to_json_at(d)` её переопределяют.

### JSON {#json}

`--profile-json out.json` (или `RunProfile::to_json()`) записывает один документ на запуск
(в сокращении):

```json
{
  "origin_depth": 3,
  "stages": [{
    "name": "ctc_head", "wall_ms": 463.8, "gpu_ms": 444.2, "dispatches": 519, "meta": {},
    "kernels": [{
      "name": "r_128_3_32_4_2_2_2_4_4_192_2", "count": 1, "total_ms": 6.3, "mean_us": 6269.1,
      "origin": "ctc_head.GigaAmCtcJit.layers.3 @ add model/src/gigaam/encoder.rs:596",
      "origin_id": 41, "origins": ["…"], "origin_ids": [41, 39]
    }],
    "origins_exclusive": [{ "path": "ctc_head.GigaAmCtcJit.layers.3", "count": 32, "total_ms": 27.8, "mean_us": 869.8, "percent": 6.3, "kernels": [] }],
    "origins_inclusive": []
  }],
  "origins": [{ "id": 41, "parent": 40, "frame": { "Module": { "name": "layers.3" } } }]
}
```

Строки ядер различаются по точке входа *и* основному происхождению, поэтому одна и та же
программа появляется по разу на каждый скоуп, который её запускал. `origins` содержит только
кадры, на которые ссылался запуск, замкнутые по `parent`, так что идентификаторы
разрешаются без процесса, записавшего файл.

## Потоки {#threads}

Состояние захвата — своё у каждого потока: переключатель, текущий скоуп и то, является ли
этот скоуп кадром вызова. Скоупы не следуют за работой в другие потоки; guard скоупа —
`!Send` и восстанавливает тот поток, в котором был открыт. Отсюда правила:

- Стройте граф в том потоке, который открыл скоупы. GigaAM и Whisper так и делают; скоуп
  стадии, открытый вокруг `prepare_with_config`, покрывает всё, что построено внутри.
- Планирование и компиляция выполняются отсоединённо (`OriginScope::suspend`) — и в
  вызывающем потоке, и в воркерах rayon, — так что окружающий скоуп никогда не просачивается
  в тело ядра; к этому моменту атрибуция уже собрана на CALL.
- Чтобы перенести скоуп в воркер, который вы запускаете сами, захватите `origin::current()`
  (`Option<OriginId>`) и установите его там через `origin::install(id)`. Воркеры
  инициализируют свой переключатель из `SVOD_ORIGIN`, как и любой другой поток.
- Поиск BEAM выполняется в дочернем процессе над телами ядер без происхождения; он никогда
  не видит скоупов.
- **Асинхронный код:** скоупы должны быть вложенными, поэтому не держите скоуп через
  `.await`. Откройте скоуп, синхронно постройте граф, освободите его, а затем ждите. Guard —
  `!Send`, поэтому future, удерживающую его через await, нельзя запустить на
  многопоточном исполнителе, а отладочная сборка паникует, когда две задачи чередуют скоупы
  в одном потоке (guard освобождается, пока более поздний ещё активен). Построение графа в
  svod синхронно, так что естественная форма кода уже этому удовлетворяет.

## Издержки и компромиссы {#costs-and-trade-offs}

- **Выключено:** ничего. Одно чтение thread-local на узел, никаких аллокаций, хеши не
  меняются.
- **Включено:** одно интернирование на вход в скоуп (мьютекс над ареной, сотни раз за
  прямой проход), одна запись thread-local на публичную операцию для кадра вызова и одна
  топологическая сортировка на ядро на разрезе, чтобы собрать объединение. Число запусков
  и время GPU у GigaAM одинаковы с включённым и выключенным захватом.
- **Меняется идентичность.** Происхождение — часть идентичности узла, поэтому два
  одинаковых выражения, построенных под разными скоупами, остаются двумя узлами, пока разрез
  их не снимет. Программ ядер это не касается — снятие восстанавливает дедупликацию, — но
  помощник, который заново строит одно и то же выражение в каждом месте вызова (обрезку
  маски, приведение таблицы, копию входа), материализует его по разу на скоуп. Запускайте
  такие помощники под `OriginScope::suspend()` или позвольте копии унаследовать
  происхождение производителя; `custom_kernel` уже делает последнее для своих входов.
  Константы, буферы, параметры, `UNIQUE`, `DEFINE_VAR`, `BIND`, `STACK` и каждый узел типа
  `Index` по той же причине никогда не несут происхождения.
- **Тесты, полагающиеся на структурную идентичность** (два построенных вручную графа,
  которые должны схлопнуться через hash-consing в один узел), стоит запускать с
  `capture_for_thread(false)`.

## Как это работает, в одном абзаце {#how-it-works-in-one-paragraph}

Каждый `UOp`, построенный при активном скоупе, хранит 4-байтовый `OriginId` скоупа
(`NonZeroU32`, так что `Option` по-прежнему занимает четыре байта) и подмешивает его в свой
хеш содержимого, поэтому одинаковые подграфы из разных скоупов остаются различными на
протяжении rangeify. На разрезе на ядра `split_store` один раз обходит тело, берёт
происхождение записываемого значения как основное, а объединение — как множество,
проставляет оба в `CallInfo` ядерного `CALL` и перестраивает тело с очищенным
происхождением. Всё после разреза — оптимизатор, BEAM, кодогенерация, все кеши ядер — видит
AST без происхождения. План копирует атрибуцию CALL на каждую подготовленную операцию,
профайлер — на каждый `KernelProfile`, а сводки обрезают цепочку родителей до запрошенной
глубины.
