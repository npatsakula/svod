# Профилирование на CUDA

[Многоуровневый профайлер](../../tile-kernels/profiling.md) нейтрален к бэкенду
выше хендлов `DispatchTimestamps` и `KernelResources`. Эта страница — о том, что
CUDA-бэкенд кладёт в эти хендлы и какие уровни существуют.

| Уровень | На CUDA | Источник |
|---|---|---|
| **1 — время на устройстве** | да | пары CUDA-событий вокруг каждого запуска |
| **2 — roofline** | да | нейтрально к бэкенду (прикидка FLOP по IR, буферы плана) |
| **3 — статическая занятость** | да | `cuFuncGetAttribute` + `cuOccupancyMaxActiveBlocksPerMultiprocessor` |
| **4 — аппаратные счётчики** | **нет** | нужен CUPTI; не привязан |

```bash
SVOD_DEVICE=CUDA:0 SVOD_PROFILE_ITERS=20 cargo run --release -p svod-model --example gigaam_infer -- ./audio.wav
```

---

## Уровень 1: таймстампы событий

`CudaPlanCtx::dispatch` при заданном `profile` записывает **таймерное событие**
до и после запуска на стриме плана и возвращает `CudaDispatchTimestamps`,
владеющий обоими. `timestamps_ns` обязан сообщать наносекунды по часам GPU,
поэтому он вычисляет

```text
start    = cuEventElapsedTime(base_event, start_event)   // мс с момента открытия устройства
duration = cuEventElapsedTime(start_event, end_event)
end      = start + duration
```

Базовое событие записывается один раз в `CudaDevice::open` и является нулём
таймлайна. Длительность измеряется напрямую между парой (полное разрешение
событий, около половины микросекунды); абсолютная позиция проходит через
`f32`-счёт миллисекунд, который грубеет по мере старения процесса, — именно
поэтому `end` выводится из `start`, а не измеряется относительно базы. Оба
события должны завершиться (`cuEventQuery`), иначе хендл сообщает `None`.

Переигрывания графов профилируются так же: `replay_profiled` запускает
исполняемую цепочку с узлом записи события до и после каждого ядра и возвращает
по одному хендлу на захваченное ядро ([Архитектура](./architecture.md)).

`Program::execute_timed`, используемый BEAM, — это та же пара событий на стриме
диспетчеризации, возвращаемая как `Duration`.

## Уровень 3: статические ресурсы

`CudaProgram::resource_usage` заполняет `KernelResources` из атрибутов функции,
прочитанных при загрузке:

| Столбец | Поле | Источник |
|---|---|---|
| `VGPR` | `vgprs` | `CU_FUNC_ATTRIBUTE_NUM_REGS` (регистров на поток) |
| `SGPR` | `sgprs` | `-` (у NVIDIA нет скалярного регистрового файла) |
| `LDS` | `lds_bytes` | `CU_FUNC_ATTRIBUTE_SHARED_SIZE_BYTES` (статический `.shared`) |
| `scratch` | `scratch_bytes` | `CU_FUNC_ATTRIBUTE_LOCAL_SIZE_BYTES` (`.local` на поток) |
| `occ%` | `occupancy` | `cuOccupancyMaxActiveBlocksPerMultiprocessor(block) × block / максимум потоков на SM` |

`wave_size` — это размер варпа устройства (32). Запросу занятости нужен размер
блока: программа запоминает блок своего **последнего запуска** и до первого
запуска откатывается к `maxThreadsPerBlock` функции. В отличие от цифры AMD,
ограниченной только регистрами, счёт драйвера уже учитывает регистры,
разделяемую память и лимит блоков на SM.

## Уровень 4: недоступен

Привязки CUPTI нет, поэтому `PlanContext::pmc_available()` на CUDA — `false`.
Установка `SVOD_PMC=1` не приводит к ошибке: профайлер деградирует до уровней
1-3 и печатает свою однострочную заметку о недоступности счётчиков.
Перечисление `PmcCounter` сегодня специфично для AMD SQ; его расширение — часть
[дорожной карты](./limitations.md).

Для экспериментов с замерами времени внутри ядра
`svod_codegen::llvm::nvptx::globaltimer()` строит узел `CUSTOM`, читающий
`%globaltimer` — наносекундные часы GPU.
