# Ограничения и дорожная карта

Чего бэкенд ещё не делает, с конкретной причиной в исходниках, и что
запланировано. Ничто здесь не падает молча: каждый пробел — это либо аккуратная
ошибка, либо задокументированный откат.

---

## Не реализовано

| Пробел | Сегодня | Где |
|---|---|---|
| **Преобразования fp8** | Каст в `FP8E4M3` / `FP8E5M2` или из них падает на рендеринге (`NVPTX fp8 cast ...`); интринсики `cvt.*.e4m3x2` для sm_89 не выдаются. Строки fp8 `mma.sync` в `resolve_mma` есть, но накормить их нечем. | `codegen/src/llvm/nvptx/ops.rs` |
| **Освобождения в порядке стрима** | `cuMemFree*` синхронизирует всё устройство и блокирует на это время вызовы драйвера из всех остальных потоков; при `LruAllocator` `_free` случается редко, но `cuMemFreeAsync` не привязан. | `device/src/cuda/allocator.rs` |
| **Копии peer-to-peer** | `cuMemcpyPeerAsync` / `cuDeviceCanAccessPeer` не привязаны. Копия `CUDA:0 → CUDA:1` идёт в исполнителе по `SyncStrategy::PeerToPeer`, который откатывается к `Buffer::copy_from`; два аллокатора — это два устройства, так что байты проходят через хостовый `Vec`. | `runtime/src/executor.rs`, `device/src/buffer.rs` |
| **Динамическая разделяемая память** | Запуски передают `shared_mem_bytes = 0`; используется только статический `.shared`, а `cuFuncSetAttribute(MAX_DYNAMIC_SHARED_SIZE_BYTES)` никогда не вызывается, так что ядро, которому нужно больше дефолтного лимита на блок, падает на JIT. Фабрика устройств заранее отказывает устройству, чей лимит ниже `shared_max` профиля (48 КиБ). | `device/src/cuda/program.rs`, `runtime/src/devices/cuda.rs` |
| **Матричные пути Hopper / Blackwell** | Опускается только `mma.sync` (`m16n8kK`); ни `wgmma`, ни `tcgen05`. | `codegen/src/llvm/nvptx/wmma.rs` |
| **Cubin'ы на хостах без `ptxas`** | Без тулкита CUDA кэш объектов хранит текст PTX, и каждая свежая загрузка платит за JIT драйвера (который драйвер кэширует в `~/.nv/ComputeCache`). Встроенного ассемблера нет: `ptxas` используется, когда он установлен (`object_format: cubin-v1`), иначе работу делает драйвер. | `runtime/src/cuda/compile.rs` |
| **Userspace-драйвер NV** | `ops_nv` из tinygrad (прямая отправка в GPU-FIFO) требует сгенерированного ABI под каждую ветку драйвера; Svod остаётся на стабильном API `libcuda.so.1`. `NV` намеренно *не* принимается в `SVOD_DEVICE` (принимаются только `CUDA` и `GPU`); имя зарезервировано под этот будущий бэкенд. | `device/src/registry.rs` |

Скорее численные замечания, чем пробелы: f64 `Exp2` / `Log2` и все
трансцендентные функции идут полиномиальным путём ([Кодген](./codegen.md));
`lg2.approx.f32` доступен рендереру, но обычными графами не используется.

## Требования, которые сегодня не обсуждаются

- Драйвер должен быть не ниже CUDA 12.0 / R525: точки входа CUDA-графов
  привязаны по их версионированным именам из 12.0, и с более старым драйвером
  бэкенд молча остаётся незарегистрированным. Фиксация PTX ISA
  (`--cuda-feature`) следует вычислительной способности — 7.8 вплоть до sm_88,
  8.4 на sm_89 и sm_90 (CUDA 12.4 / R550), далее 8.6, 8.7 и 8.8 по линейке
  Blackwell (вплоть до CUDA 12.9), — так что карта Blackwell поднимает порог до
  драйвера своей ISA, а более новый clang — нет.
- `clang` обязан нести таргет NVPTX; отката на NVRTC нет.

## Дорожная карта

Что осталось, в порядке приоритета:

1. **Освобождения в порядке стрима**: `cuMemFreeAsync` на копирующей полосе для
   памяти устройства, чтобы освобождение перестало дренировать устройство.
2. **Настоящий P2P**: привязать `cuDeviceCanAccessPeer` /
   `cuCtxEnablePeerAccess` / `cuMemcpyPeerAsync` и направить
   `SyncStrategy::PeerToPeer` через них.
3. **fp8**: опустить интринсики `cvt` для sm_89, чтобы строки fp8 `mma.sync`
   стали достижимы, и позволить `for_cuda_arch` строить профиль sm_89.
4. **Динамическая разделяемая память** через `cuFuncSetAttribute`, чтобы ядро
   могло выйти за стандартный предел 48 КиБ на блок.

Синхронизация с областью видимости и аппаратные счётчики CUPTI были двумя
другими пунктами; оба уже готовы ([Архитектура](./architecture.md),
[Профилирование](./profiling.md)).
