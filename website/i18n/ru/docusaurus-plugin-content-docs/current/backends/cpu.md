# CPU-бэкенд

CPU-бэкенд компилирует каждое ядро в нативный машинный код во время выполнения
и вызывает его в процессе. У него два пути кода, выбираемых через
`SVOD_CPU_BACKEND`:

| `SVOD_CPU_BACKEND` | Рендерер | Компилятор | Бэкенд кэша |
|---|---|---|---|
| `llvm` (по умолчанию; выбирается и при пустом или незаданном значении) | Текст LLVM IR (`codegen/src/llvm/cpu/`) | libLLVM, привязанный в процессе, или `clang -x ir`, если его не удаётся загрузить | `cpu-llvm-inprocess` / `cpu-llvm-clang` |
| `clang` | Исходник на C (`codegen/src/c/`, диалект Clang) | подпроцесс `clang -x c` | `cpu-clang` |

Принимаются только эти два написания и их формы в верхнем регистре
(`CpuBackend::parse`); всё остальное пишет предупреждение в лог и выбирает
LLVM. Оба пути выдают перемещаемый ELF-объект, который
[JIT-загрузчик](./jit-loader.md) отображает и релоцирует в памяти; ни один из
них не пишет временный файл и не `dlopen`-ит разделяемую библиотеку. Связка
находится в `runtime/src/devices/cpu.rs`.

Фабрика устройства `"CPU"` регистрируется безусловно, и CPU является
устройством по умолчанию везде, кроме macOS, где им является `METAL:0`
(см. [Бэкенды](./overview.md)).

## Путь LLVM

Рендерер выдаёт по одной LLVM-функции на ядро: буферы — параметрами
`ptr noalias align 32`, скаляры — `i32`, с атрибутами
`nounwind "no-builtins" "no-trapping-math"="true"`:

```llvm
define void @r_64_32(ptr noalias align 32 %data0, ptr noalias align 32 %data1, i32 %core_id) #0 {
entry:
  ...
  ret void
}
```

### libLLVM в процессе

`runtime/src/llvm_inprocess.rs` привязывает LLVM-C API из разделяемой libLLVM
через `libloading`. Библиотека ищется один раз за процесс в таком порядке:

1. `SVOD_LLVM_LIB=<path>` — тогда этот файл единственный кандидат;
2. `llvm-config --libdir`, соединённый с каждым именем-кандидатом;
3. каждое имя-кандидат через собственный путь поиска динамического загрузчика;
4. на macOS — `/opt/homebrew/opt/llvm/lib/libLLVM.dylib` и версионированные
   keg'и `llvm@N`.

Имена-кандидаты — `libLLVM.so` / `libLLVM.dylib`, затем для каждой мажорной
версии от 30 до 16 — SONAME дистрибутивов (`libLLVM.so.N.1`, `libLLVM-N.so.1`,
`libLLVM-N.so`, `libLLVM.so.N`; `libLLVM-N.dylib`, `libLLVM.N.dylib`). Версия
читается через `LLVMGetVersion` и должна быть **16 или новее**.

Компиляция разбирает IR из буфера в памяти (`LLVMParseIRInContext`), проверяет
его, запускает `LLVMRunPasses("default<O2>")` с включёнными развёрткой циклов,
векторизацией циклов и SLP-векторизацией и выдаёт объект через
`LLVMTargetMachineEmitToMemoryBuffer`. Целевая машина —
`<arch>-none-unknown-elf` с именем CPU хоста и строкой фич
(`LLVMGetHostCPUName` / `LLVMGetHostCPUFeatures`), PIC-релокациями и моделью
кода по умолчанию; на macOS aarch64 к строке фич добавляется `+reserve-x18`.
Диагностики уровня error из обработчика контекста проваливают компиляцию.
Каждый поток владеет `Session` (контекст, целевая машина, data layout, опции
проходов) в thread-local, поэтому ядра компилируются параллельно.

`SVOD_LLVM_INPROCESS=0` (ровно значение `0`) отключает путь в процессе. Любая
неудача привязки библиотеки — не найдена, слишком старая, нет символа —
откатывается на clang-продюсер ниже; откат пишется в лог на уровне `warn`,
если только переменная не отключила путь намеренно.

:::note[Одна libLLVM на процесс]
Фреймворк компилятора Metal от Apple загружает собственную libLLVM с
`RTLD_GLOBAL`, которая не может делить процесс с другой копией. Поэтому
CPU-бэкенд и [Metal](./metal.md)-бэкенд разыгрывают один слот
(`svod_device::claim_inprocess_llvm`): кто первым компилирует, тот его и
сохраняет, а второй берёт свой запасной путь через подпроцесс или публичный API.
:::

### Запасной путь через clang

`compile_ir_to_object_with` прогоняет IR через clang, из stdin в stdout:

```text
clang -x ir -c -O2 -march=native -fPIC -fno-math-errno -fno-stack-protector \
      -funroll-loops -fvectorize -fslp-vectorize --target=<arch>-none-unknown-elf [-ffixed-x18] - -o -
```

У продюсера в процессе и clang-продюсера разные идентичности в кэше объектов
(`cpu-llvm-inprocess` с `library=<path>;version=x.y.z` и CPU/фичами хоста
против `cpu-llvm-clang` с идентичностью clang), поэтому объекты никогда не
переходят между продюсерами.

## Путь clang C

`SVOD_CPU_BACKEND=clang` рендерит вместо этого C — `void name(T* restrict data0, ...,
const int dataN)` с математикой через `__builtin_*` — и компилирует его командой

```text
clang -c -x c -O2 <cpu flag> -fPIC -ffreestanding -fno-math-errno -fno-stack-protector \
      -nostdlib -fno-ident --target=<arch>-none-unknown-elf [-ffixed-x18] - -o -
```

где `<cpu flag>` — это `-march=native` на x86_64 и loongarch64, `-march=rv64g`
на riscv64 и `-mcpu=native` в остальных случаях (на ARM `-march=native` задаёт
только семейство ISA). Исходник читаем, ради этого путь и существует: можно
посмотреть, что делает ядро, не читая LLVM IR.

`clang` ищется только в `PATH` (`ClangToolchain::discover`); переопределения
через `SVOD_CLANG` или `CC` нет. Его идентичность для кэша объектов —
`path=...;sha256=<binary digest>;version=<clang --version>`, а путь C
дополнительно записывает разрешённые `-target-cpu` и фичи из `clang -###`
(с отпечатком `/proc/cpuinfo`, когда флаг говорит `native`), поэтому объект,
скомпилированный на одной машине, не переиспользуется на другом CPU.

:::tip[Запасной путь через dlopen]
Cargo-фича `dlopen-fallback` крейта `svod-runtime` заменяет ELF-загрузчик
**только для пути C**: `clang -shared ... -lm` пишет `kernel.so` во временный
каталог, который открывает `libloading`. Это медленнее и существует для
платформ, где загрузчик в памяти не работает; кэш объектов записывает его как
`elf-shared-dlopen-v1`, а CI прогоняет его как проверку `test-dlopen-fallback`.
Путь LLVM всегда использует загрузчик в памяти.
:::

## Математика

Рендереры CPU сохраняют трансцендентные функции: `exp`, `log`, `sin`, `cos`,
`tan`, `pow` и родственные рендерятся как интринсики `@llvm.*` или вызовы
`__builtin_*`. `sqrt`, `fma`, `floor`, `rint` и подобные понижаются в
инструкции; остальные становятся вызовами `libm`, которые загрузчик разрешает
через `dlsym(RTLD_DEFAULT)` во время загрузки. Путь LLVM убирает `Erf` из своих
поддерживаемых операций (он декомпозируется), путь C его сохраняет; оба
исключают `Threefry` и `Max`, которые декомпозируются в голый XOR и select.

## Потоки

`SVOD_THREADS` (положительное целое; по умолчанию — доступный параллелизм
хоста) — это единый бюджет потоков. Он задаёт размер глобального пула rayon,
который параллельно компилирует промахи кэша ядер и исполняет CPU-ядра, и он же
является **разбиением по `core_id`** по умолчанию для каждого CPU-ядра:

- THREAD-опт оптимизатора (`schedule/src/optimizer/opts.rs`) переносит одну
  глобальную ось цикла в самую внешнюю позицию и разбивает её; эвристика
  пробует 32, 16, 12, 8, 6, 5, 4, 3 и 2 части, ограниченные бюджетом и одной
  частью на 131072 элемента, и берёт первое число, делящее ось (иначе ось
  дополняется). Разбиение вшивается в ядро и его идентичность в кэше.
- `gpudims` понижает эту ось в переменную `core_id` в `[0, N-1]` вместо
  `gidx`/`lidx`, а `global_size[0]` становится `N`.
- Во время выполнения `execute_kernel` видит `global_size[0] > 1` и запускает
  `(0..N).into_par_iter()`, вызывая один и тот же указатель на функцию с теми
  же буферами и перезаписанным для каждой задачи `core_id`. Каждый `core_id`
  пишет непересекающийся диапазон вывода, поэтому синхронизация не нужна.
  Внутри уже работающего воркера rayon цикл выполняется последовательно, без
  вложенности.

Разбиение ядра и размер пула могут различаться: ядро, разбитое на 8 частей,
корректно работает на 4 потоках. `SVOD_THREADS=1` отключает разбиение. Rayon
строит глобальный пул один раз, поэтому побеждает размер первого вызывающего,
а более поздний отличающийся запрос пишет одно предупреждение
(`ensure_thread_pool`). `RAYON_NUM_THREADS` не учитывается.

## Вызов ядра

Загруженное ядро — это `JitKernel` (путь C, реэкспортируется как
`ClangKernel`) или `LlvmKernel`: отображённый объект, указатель на точку входа,
имена переменных и `KernelCif`. ABI — `void kernel(ptr..., i32...)` в порядке
слотов ABI: параметры хранилища — `Type::pointer()`, скаляры — `Type::i32()`, а
значения `i64`, которые несёт исполнитель, усекаются до `i32`. Сам вызов идёт
через **libffi** (`cif.call(CodePtr(fn_ptr), &args)`, `runtime/src/dispatch.rs`),
и поэтому сигнатура может меняться от ядра к ядру без transmute на каждую
арность.

У CPU нет фабрики графов, контекста плана и временных меток: каждое ядро — это
синхронный вызов, `wait` игнорируется, а уровень времени устройства в
профилировщике — это wall-clock.

## Кэш объектов

Скомпилированные объекты кэшируются на диске (`runtime/src/object_cache.rs`)
в `SVOD_OBJECT_CACHE_DIR`, иначе в `$XDG_CACHE_HOME/svod/objects`, иначе в
`~/.cache/svod/objects`; `SVOD_OBJECT_CACHE=0` отключает его, а
`SVOD_OBJECT_CACHE_MAX_BYTES` задаёт бюджет (по умолчанию 1 GiB, вытеснение
самых старых по mtime). Ключ записи — SHA-256 исходника и `CompilerIdentity`
(`schema`, `backend`, `target_architecture`, `toolchain`, `flags`, `abi`,
`object_format`); запись хранится как `<hex>.obj` с magic, ключом, дайджестом
полезной нагрузки и самой нагрузкой; проваленная проверка целостности считается
промахом. Каждый объект, из кэша или свежий, перед загрузкой проверяется на
соответствие ELF-архитектуре хоста, порядку байтов, виду объекта и символу
точки входа. Тот же кэш хранит объекты AMD, CUDA и Metal под их собственными
идентичностями.

## Переменные окружения

| Переменная | По умолчанию | Эффект |
|---|---|---|
| `SVOD_CPU_BACKEND` | `llvm` | `clang` выбирает путь C |
| `SVOD_LLVM_INPROCESS` | вкл. | `0` принудительно включает подпроцесс `clang -x ir` |
| `SVOD_LLVM_LIB` | не задана | Путь к libLLVM для привязки; если задана — единственный кандидат |
| `SVOD_THREADS` | параллелизм хоста | Бюджет потоков и разбиение по `core_id` по умолчанию |
| `SVOD_OBJECT_CACHE` | вкл. | `0` отключает дисковый кэш объектов |
| `SVOD_OBJECT_CACHE_DIR` | `$XDG_CACHE_HOME/svod/objects` | Перемещает кэш |
| `SVOD_OBJECT_CACHE_MAX_BYTES` | 1 GiB | Бюджет кэша |
| `SVOD_DUMP_LLVM_IR` | не задана | Каталог, куда пишется отрендеренный LLVM IR каждого ядра |
| `SVOD_DUMP_POST_O2_IR` | не задана | Каталог, куда пишется IR после конвейера `-O2` clang |
| `RUST_LOG` | не задана | `svod_runtime=debug` сообщает, какой продюсер компилирует (libLLVM или clang), и логирует каждую компиляцию и загрузку ядра; непреднамеренный откат на clang — это `warn` |
